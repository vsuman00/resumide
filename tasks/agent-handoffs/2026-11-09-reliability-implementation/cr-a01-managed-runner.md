# CR-A01 managed runner

The [runner](../../../scripts/verify-managed-document-worker.ts) implements the consumer sequence in the [managed validation action](cr-a01-managed-validation-action.md). It starts the production app build on loopback, uploads a real two-page PDF with a blank second page, and leaves the first lease to expire. It then calls the normal analysis and privacy workers, verifies owner-only evidence and the measured page count, and checks exact Storage and synthetic Auth absence. An interrupted run leaves its private fixture ledger for reconciliation.

## Run the coordinated verification

After the dedicated project is approved and the exact 93-operation replay is recorded, use the [coordinator](../../../scripts/run-managed-document-worker-verification.ts). It verifies both SQL source hashes, checks readiness on the approved target, starts the worker with a sealed environment, and binds the read-only cleanup audit to the exact run's ledger. The older direct commands below remain available to operators who need to inspect an individual step.

Provide the isolated project's `SUPABASE_URL`, publishable and secret keys, `MANAGED_DB_PASSWORD`, and the absolute `MANAGED_DB_CA_FILE`. Set `MANAGED_WORKER_AUTHORIZATION=exclusive-project-worker-and-privacy-fixtures`, choose a fresh UUID as `MANAGED_WORKER_RUN_ID`, and set `APP_ORIGIN` to an unused HTTP loopback port. Set `MANAGED_DB_APPROVAL` to a JSON object with `schemaVersion` equal to `managed-db-document-worker-approval/1`, `purpose` equal to `cr-a01-document-worker`, the exact `targetUrl` and `connectionHost`, the 93-operation `orderedDigest` from the action, and `exclusiveSyntheticProject: true`. The approval records the independently reviewed isolated target and replay. [Supabase PostgreSQL connections](https://supabase.com/docs/guides/database/connecting-to-postgres)

```sh
RESUMIDE_PRIVATE_VERIFY=aa7-owned-synthetic npm run build
node --experimental-strip-types scripts/run-managed-document-worker-verification.ts
```

Exit 0 requires matched readiness, one two-page lifecycle with a reclaimed lease, and an independent SQL cleanup receipt. Exit 1 reports the failed stage. Exit 2 reports unavailable admission. The coordinator preserves the private run directory. Reconcile any started run before attempting another. It passes Supabase API credentials to the worker and keeps the PostgreSQL password with the SQL client. AI stays disabled.

The verifier owns the local app through an IPC channel. On a normal run, it closes that channel and requires the app to exit cleanly before allowing the success receipt. If the verifier is killed or reaches its deadline, the lost channel triggers the app's normal shutdown with a bounded drain. An interrupted worker still requires reconciliation of the private ledger and any hosted requests already in flight. [Node.js IPC child processes](https://nodejs.org/api/child_process.html)

## Run the protected CI job

Once the target and exact 93-operation replay are approved, configure the `managed-supabase-document-worker` environment for the reviewed protected branch. Use environment variables for `MANAGED_WORKER_AUTHORIZATION`, `MANAGED_DB_APPROVAL`, `MANAGED_DB_CA_PEM`, `SUPABASE_URL`, and `SUPABASE_PUBLISHABLE_KEY`. Use environment secrets for `MANAGED_DB_PASSWORD`, `SUPABASE_SECRET_KEY`, and `MANAGED_WORKER_LEDGER_KEY`. The recovery key is a canonical base64 encoding of 32 randomly generated bytes. Keep it available through the recovery window. [GitHub environment controls](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)

Run **CI** manually with **Managed verification suite** set to `document-worker`. The `managed-document-worker` job runs the coordinator after quality passes. The other managed verification suites remain unavailable in that dispatch. The worker uses its own approval profile and serializes with the existing managed suites.

On failure, the job attempts to seal the private admission file and fixture ledger into a single authenticated encrypted artifact with seven-day retention. Cancellation and runner loss can prevent upload. If a started run has no archive, keep the target out of further fixture runs until its state is reconciled. [GitHub workflow cancellation](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-cancellation)

To recover, supply the original target URL in `SUPABASE_URL` and the original `MANAGED_WORKER_LEDGER_KEY` through the private process environment. Then run the following command on the downloaded archive.

```sh
node --experimental-strip-types scripts/manage-document-worker-archive.ts --recover document-worker-ledger.enc
```

Recovery returns the run ID and restores its exact files under `/tmp/resumide-managed-<run-id>/`. It refuses a different target, altered ciphertext, or any overwrite of differing local evidence. Use the restored ledger to reconcile the managed target before retrying. Recovery itself performs no hosted writes.

A real two-page synthetic PDF reproduced the failure through the production extractor and evidence reader. The correction history correctly reported zero pages because the fixture had no corrections.

It also checks that the evidence retains the correct page order, including the blank second page, and withholds scoring. The built evidence route must return private, non-cacheable HTML to the owner with both pages visible. The second signed-in account must receive a private 404 without fixture evidence. The coordinator requires the new route verification field in the worker receipt.

## Verify the candidate deletion form

The earlier runner called the deletion service directly. It now submits the candidate's authenticated `POST /privacy` form and requires a private response acknowledging the queued deletion. The runner records the request correlation ID before submitting the form. It uses the exact audit event to resolve the queued deletion for the same owner and organization. The coordinator checks that the ledger ties the original correlation ID to the deletion ID used in the cleanup audit.

If the response or audit linkage is missing or ambiguous, the runner stops before starting the privacy worker. Keep the intent record and reconcile the exact owner and request correlation ID before another fixture run. The correlation ID identifies the request attempt for audit and reconciliation.

## Run inputs

Admit the dedicated project separately and apply the exact [93-operation packet](managed-schema-worker-successor-93.json). Use the project's read-only post-replay result as `postReplay` in `worker-admission.json` within the existing managed fixture directory. Set the other receipt fields to `targetUrl`, `runId`, `orderedDigest` from the packet, and `authorizedScope` with the value `exclusive-project-worker-and-privacy-fixtures`. The receipt records the separate approval and preflight steps. It supplies no independent proof of isolation.

Use `MANAGED_TEST_PURPOSE=cr-a01-document-worker`, `MANAGED_TEST_CAPABILITY=owned-fixtures` and `MANAGED_TEST_AUTHORIZATION=synthetic-owned-records-only` for Auth fixture setup. Bind `MANAGED_TEST_TARGET_URL` to `SUPABASE_URL` and set `MANAGED_TEST_RUN_ID` to the receipt UUID. Set `MANAGED_TEST_LEDGER` to `/tmp/resumide-managed-<run-id>/fixtures.jsonl`. The directory uses mode `0700`, and the empty ledger and receipt use `0600`. Reconcile a started ledger before a new run. Keep credentials in the private test process environment.

Set `APP_ORIGIN` to an unused `http://127.0.0.1:<port>`. Enable the four analysis flags in the [action](cr-a01-managed-validation-action.md). Set `AI_ENABLED=false`, `OPENAI_API_KEY=build-ai-harness-no-live-key`, and `OPENAI_BASE_URL=https://api.openai.com/v1`. Keep optional provider features off. Run the preflight and build before invoking the runner under Node.js 22.

```sh
export RESUMIDE_PRIVATE_VERIFY=aa7-owned-synthetic
npm run build
node node_modules/vite-node/vite-node.mjs --config vitest.config.ts scripts/verify-managed-document-worker.ts
```

After the run, reconcile the fixture's private admission and retained metadata using the managed action. The runner verifies Auth, Storage and selected application rows. The write barrier and rate-limit row follow their normal retention checks. Managed execution and CR-A01 acceptance remain open. [Local verification receipt](cr-a01-managed-runner-evidence.json)
