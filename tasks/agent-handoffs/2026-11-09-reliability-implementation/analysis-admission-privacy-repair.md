# Account deletion hold and upload export coverage

**CR-R19 remains partial.** This change closes the false completion path for owned upload-admission history and adds that history to newly completed account exports. The next repair is physical cleanup and erasure of the records. Recorded on 2026-11-21 against dirty `main` at `a0b239299d75b0bd64b588fe743ebe2975fb28b9`.

The owner asked to proceed after the recommendation to erase upload operation IDs and hashes after verified cleanup. That is the working policy for implementation. The existing 30-day rule continues to govern AI accounting under [ADR-0020](../../../docs/decisions/0020-owned-ai-accounting-retention.md).

- The migration fences new entries in both admission tables with the existing candidate write lock. A deletion request with admission history cannot commit a new plan or mark a privacy step complete. An existing plan receives the same check. If the guard rejects, the transaction restores the prior request status, worker claim, and candidate data. The migration verifies step coverage and restricts direct step writes. The existing fenced RPC bodies and their catalogue seal are preserved. [Migration](../../../supabase/migrations/20261121091814_analysis_admission_privacy_guard.sql).
- Newly completed owner exports include explicitly selected operation and upload fields across organizations, including abandoned uploads without source rows. Both collections come from one database snapshot. An invalid manifest or oversized snapshot rolls completion back. Earlier completed exports and backup copies still need lifecycle review.
- The worker records an allowlisted hold code. The privacy page explains the hold and distinguishes an unavailable request history from an empty list. Existing completion labels identify request processing, and full account erasure still requires verification. [Worker](../../../app/lib/server/privacy-worker.ts) · [Privacy page](../../../app/routes/privacy.tsx).

A disposable PostgreSQL 17 server with a private local socket reproduced the pre-change deletion defect and verified transactional rollback, old and new plans, stale claims, exact owner-scoped exports, requeue, and direct privileges. The two-session check proved that a held deletion lock prevents a new admission insert and that a held writer lock prevents deletion preparation from proceeding. The harness extracted the existing preparation and completion functions and used synthetic schema fixtures for unrelated dependencies. [Reproduction harness](analysis-admission-privacy-native-harness.py.txt).

Across three test reports, 6,747 tests in 323 files passed. The first full invocation had seven harness failures. The macOS process tests needed their own sandbox boundary, and the extraction tests needed the repository's synthetic configuration. Both sets passed under those conditions without assertion or source changes. Type checking, formatting for affected files, lint (four existing warnings), and the web and worker builds passed. [Verification receipt](analysis-admission-privacy-repair-receipt.json).
