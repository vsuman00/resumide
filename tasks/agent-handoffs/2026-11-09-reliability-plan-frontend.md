## Reviewed correction contract before code

The existing canonical design imports unconfirmed original assertions and deliberately leaves evidence corrections in a separate ledger. The owner now requests real propagation. Root must review an explicit product/schema/ADR amendment before implementing that changed contract; do not silently rewrite the old requirement or the failed receipt.

A latest applicable correction is scoped to the same owner, active source hash, evidence attempt, correction revision and stable assertion/entity target slot. It is never simply the latest value for a field across a whole resume. Employer/role/date entries need entity grouping; a field-wide legacy correction with ambiguous targets requires explicit candidate target selection. A missing target needs an explicit candidate-authored add path. Unmappable corrections remain visible and actionable rather than disappearing or replacing every employer.

Materialize a corrected value with candidate-authored provenance referencing the correction event and source/attempt binding. Preserve raw evidence and the original assertion. Do not fabricate a source citation for the new value, infer missing facts, carry an old confirmation to new text or grant calibrated/verified status. Imported corrected facts start unconfirmed until the candidate separately confirms that exact canonical value. Re-import must be idempotent and must not overwrite later manual edits. Existing canonical versions require a reviewed diff and an explicit CAS child version; undo/restore append children and retain the correction/provenance history. Export remains blocked for unconfirmed/unsupported facts under the existing contract.

This agrees with the backend planner's grouped-target/projection/materialization prerequisite. Warning-only closure of CV04 is rejected. Preserve the earlier carry-or-disclose failure, then add stronger propagation/provenance tests so a notice alone cannot turn the new acceptance green.
