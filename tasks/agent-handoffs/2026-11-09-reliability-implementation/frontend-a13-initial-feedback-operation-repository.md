# A13 initial-feedback foundation RPC boundary

Implemented only the three actual Native foundation calls. No SDK, compiler, publication/read/export, shared usage counter, worker adoption, flag or legacy API changed.

`createInitialFeedbackOperationRepository(client,{ownerId,organizationId,analysisId,lease,policy},{timeoutMs?,now?})` returns `prepare(retryAfterAttemptId|null,{signal?})`, `claim(prepared,budget|null,{signal?})` and `settle(winningDispatch,{usage,errorCode},{signal?})`. Explicit scope, lease and actual source-generated policy are validated before IO. There is no environment/configuration read or policy selection fallback.

Prepare reads strict foundation metadata, then issues one prepare mutation. Claim reads fresh metadata, then issues one claim mutation. Metadata has exactly seven actual pinned strings plus schemaReady/prepareExecutable/claimExecutable/settleExecutable booleans, using the separate current foundation profile. Prepare requires its capability; claim requires both claim and settlement capability in the same reply. Staged false capabilities refuse without old-path fallback. This metadata remains diagnostic foundation admission, not full publication readiness or Native runtime proof.

Replies pass the actual backend bounded strict schemas and exact owner/organization/analysis/operation/attempt/binding/policy correlations. Native JSONB digests remain opaque. Fresh prepared policy must equal the explicit requested policy; pending replay preserves the original captured policy without rebasing. A consumed earlier retry selector may return its stored next attempt even when a later attempt exists. Pending data never becomes a fresh claim context.

Only a validated true, nonreplayed dispatched claim produces a winning handle. Prepare handles and winning handles are instance-owned WeakMap entries with independent private copies. The public dispatch has frozen scalar identities; changing returned nested operation/attempt data cannot retarget settlement. Forged, copied, cross-instance, false or ambiguous claims cannot mint a settlement handle. R03 input/envelope remains unchanged, with exact submitted attempt ID/ordinal/reservation correlation. Queue attempt is not inferred to be a provider ordinal. No claim loser is settled or released here.

Technical settlement uses the captured private identity and canonical known-string counters or null. It makes one independently bounded RPC without current content, membership, consent, month or readiness refresh. Candidate cancellation does not cancel a later separately requested technical settlement. Known counters and terminal errors are monotone; null cannot clear them, late known counters can fill a hold, and conflicting values refuse. An ambiguous settlement retains its exact input for explicit manual retry; a different input remains blocked until a correlated receipt resolves it. No automatic retry, release, refund or second R03 debit occurs.

Each method uses a 1–5000ms whole deadline, absolute clock checks and AbortController, including an ignored-abort RPC. Safe errors expose only fixed code plus mutationStatus not_sent/refused/unknown. A timeout, malformed reply or uncertain transport never invents successful mutation or permission.
