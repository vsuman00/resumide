# JD browser fixture: admission cleanup gap

Status: SOURCE FINDING; retirement implementation and actual cleanup remain open. Read-only review used dirty HEAD `a0b239299d75b0bd64b588fe743ebe2975fb28b9`. No application or SQL change, SQL parsing, database access, Auth operation or browser execution occurred. This one-file finding is separate from the runtime typing correction.

The genuine fixture enables bound HTTP admission. In the [admission migration](../../../supabase/migrations/20261110080809_analysis_admission_binding.sql), lines 3–24 declare `analysis_admission_operations.owner_id` → `auth.users` and `organization_id` → `organizations`, both `ON DELETE RESTRICT`. Upload `operation_id` restricts operation deletion; the operation's `(adopted_upload_id,id)` also restricts its adopted upload. `private.analysis_admission_identity()` and both triggers, lines 26–47, reject every row deletion and freeze adopted operation updates. Even a non-adopted intent therefore prevents later Auth deletion while its operation remains.

`public.cleanup_analysis_admission()` at lines 196–212 is the existing exact compensation authority. It accepts an owned operation/upload pair, rejects adopted uploads, and permits only unadopted `prepared → cleanup_pending → cleaned`. It neither deletes nor unlinks ledger rows. Direct table access is revoked from service_role, and only the three bounded admission RPCs are granted at lines 215–224. Turning the feature off, bypassing admission or relying on Auth cascade would not repair this lifecycle.

The current [privacy worker](../../../app/lib/server/privacy-worker.ts), `processPrivacyRequest()` at lines 286–305, prepares deletion, removes returned exact object keys and completes the request. The latest [three-argument preparation](../../../supabase/migrations/20261116075250_privacy_export_generation.sql), lines 202–271, captures AI dispositions/usage, retires feedback publications and deletes candidate content, consents, memberships and profile. It touches neither admission store and does not delete Auth or organizations. Completion at lines 113–129 only completes request bookkeeping. Its object plan reads resume versions, so abandoned admission objects are not supplied by that query. This flow cannot retire the blocking admission rows.

This is a documented adoption gap. The [privacy data map](../../../docs/security/PRIVACY_DATA_MAP.md), lines 44–47, explicitly requires abandoned/duplicate intent and orphan-object coverage, says compensation retains durable intent, and records missing purge/disposition. [CR-R17 and its CR-R19 dependency](../../reliability-remediation-plan.md#cr-r17) require exact cleanup and deletion recovery. The [runtime blueprint, RT19](../2026-11-09-reliability-plan-runtime.md#rt19-exact-cleanup-and-privacy-deletion-recovery) requires durable failed-cleanup retry and zero allowlisted residuals. The [current task sequence](../../todo.md) keeps FK-safe finalization and Auth/session/organization disposition open.

The smallest proper next source slice is a bounded admission-retirement contract and implementation tied to a real fenced owner-deletion operation. It must cover every owned intent and exact object obligation, deny retirement for unknown/in-flight outcomes, preserve retry evidence, and permit only the reviewed lifecycle transition through the immutable/circular references. Retained fields, purpose, export, disposition and restore treatment must be settled before destructive authority is enabled. Do not drop triggers, weaken ordinary identity/replay checks, add broad cascades or treat a cleanup refusal as completion.

[ADR-0020](../../../docs/decisions/0020-owned-ai-accounting-retention.md) accepts a maximum 30 days for linkable AI accounting metadata from the first durable deletion preparation. It preserves original-period usage, conservative unresolved holds and the original deadline. That scope does not automatically select a retention schedule for every analysis-admission intent; resume-root `RETENTION_DAYS` supplies none. No new retention policy or retirement implementation is introduced here. The separate Supabase target/DDL decision remains pending, and this finding grants no execution authority.
