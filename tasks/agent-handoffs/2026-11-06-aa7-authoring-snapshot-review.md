# AA7 request snapshot reuse review

Status: READ-ONLY PROPOSAL; timing pending; no implementation recommended yet. No source, service, database or provider changes. The [source-bound receipt](2026-11-06-aa7-authoring-snapshot-review.json) records the reviewed file hashes.

A successful populated score GET currently loads canonical data three times: scoring input, final scoring barrier, then authoring. Each full load performs eight queries. After the scheduling fix, a known-version load has four dependency waves; default head selection has five. These are source counts, not measured latency. Requirements and other score reads are additional.

Moving one owned load into the score route and passing its result through the existing scoring snapshot argument does not itself save a canonical read. The saving requires authoring to reuse that same snapshot. It would remove eight reads, but also remove authoring's existing fresh ownership/source/head check after scoring. Preloading first additionally serializes the score repository's currently parallel job-id query. Keep the final score canonical/requirements/analysis/job/head barrier unchanged.

The strict behavior-preserving variant may reuse immutable version/history payloads while still calling fresh ownedAnalysis and head validation for authoring. Compare fresh resume/source/organization/head to the validated snapshot before returning private data. This saves two payload queries, eight to six, with likely unchanged dependency-wave count. It cannot be assumed to fix the30-second case. Removing all eight reads requires an explicit decision that the final scoring barrier supplies the required freshness contract; it is not identical to retaining the later authoring check.

If timing justifies implementation, use only the exact request-owned snapshot already passed to a successful scoring call. Keep default no-snapshot callers unchanged. Reuse must bind analysis scope, owner, resume, canonical version/revision/head, organization and evidence/source lineage. Do not reconstruct a snapshot from public DTO fields. The score's inputSha256 is a composite digest, not the canonical inputSha256. A canonical document can retain its original analysisId across the shared resume lineage: do not tighten that field to the route analysisId and break existing behavior.

Validate all four ScoreReadOptions before route preloading. Otherwise an invalid canonical UUID changes the existing422 scoring-input error into404 canonical-not-found or extra privileged I/O; malformed expected/requirement selectors also must fail before canonical loading. Preserve unsupported/duplicate-selector handling, feature gates, authentication, no-store/cookies, historical read-only behavior and focus/history-error precedence. Keep the snapshot local to the server call; no returned DTO field, spread, logging, global cache, migration or threshold change.

Required focused regressions would cover invalid selector precedence, exact snapshot binding and read count, no-snapshot fallback, historical read-only output, held final-score head/deletion failures, authoring post-score freshness if retained, concurrent event rejection/error precedence, and unchanged serialization. Existing score snapshot and repository scheduling regressions must remain intact.

Wait for the tester's unchanged-case request timing. If the canonical payload reads are not a demonstrated bottleneck, make no change. If a proposal is implemented, compare the same flow and fixed timeout before/after without weakening assertions, and retain it only if correctness and measured latency both improve. No savings in milliseconds are claimed by this audit.
