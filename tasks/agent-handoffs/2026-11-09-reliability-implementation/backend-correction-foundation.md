## Private lock and byte primitives

SQL derives owner resources from signed first-64-bit SHA256 of UTF8 `resumide:owner-write:v1:` plus lowercase UUID. It sorts/deduplicates the actual bigint resources, not UUID order. Inputs are one-dimensional, one-based, non-null UUID batches of 1–1,024 entries; duplicate owners are harmlessly deduplicated. Private blocking/try-lock helpers take only owner UUIDs, not a production raw-key override. A false try-lock retains already held transaction locks: the future top-level caller must end that transaction and must freeze the complete owner batch before row locks. No existing writer calls these helpers yet; global claims, privacy enqueue, ingestion phantoms, retention and final cutover remain open.

The low-level JS/SQL byte codec is `c02-command-bytes/1.0.0`: ASCII `C02OP1` plus LF, then `N;` or `T<byte-length>:<UTF8>;` for each ordered atom. Null, empty, Unicode normalization, delimiters and atom boundaries remain distinct. Maximum 1,024 atoms and 65,536 total framed bytes. JS rejects non-string/non-null atoms, sparse holes, NUL and unpaired surrogates; PostgreSQL UTF8 text cannot represent the latter two. Oversized inputs reject without truncation. The encoder does not trim, sort, canonicalize JSON, normalize identifiers or verify actor/selector semantics. SQL authority must later rederive the agreed fixed-order typed atoms; a browser hash or this helper's output alone cannot admit a command.
