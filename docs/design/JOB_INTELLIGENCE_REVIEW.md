# AA3 job intelligence review

Status: **IMPLEMENTED for local engineering; domain/taxonomy release acceptance OPEN.**

`/analysis/:id/requirements` shows the exact supplied job description, proposed typed requirements, importance cues, Unicode codepoint ranges, uncertainty and immutable JD history. `JOB_INTELLIGENCE_ENABLED` defaults off. The route authenticates the owner, checks active source access and membership, revokes access for pending deletion, enforces same-origin POSTs and bounded forms, and returns private `no-store` responses.

The initial parser recognizes explicit software vocabulary, numeric experience ranges, education, certification, location, work authorization and responsibility clauses. Required, preferred and responsibility headings carry their own citations. Conflicting importance is unknown. Negation remains visible and never becomes a required positive condition. Every normalized minimum experience value must match the cited JD. Exact repeated values share a dedup group; broader semantic deduplication is not claimed. Original JD text is preserved even when a clause is not recognized.

The approved first development scope is software engineering, English, India. The server checks a conservative software-role title vocabulary; generic engineers and unrelated roles are unsupported. Recognized role titles are only domain candidates. All supported imports remain review-required with uncalibrated confidence; empty extraction is insufficient. Neither candidate title recognition nor source citations validate a domain or authorize Job Alignment scoring.

The optional model adapter has no default provider and is not enabled by this route. It may propose importance only for deterministically recognized, exactly cited requirements. Explicit importance cannot be overwritten; inferred importance carries a separate basis and review warning. Unknown fields, uncited additions, duplicate output, invented years and malformed output fall back to the deterministic baseline. Timeout and outage abort the adapter and return an explicitly flagged review child. These tests use synthetic adapters, not a live provider or model-variance study.

The taxonomy boundary ingests a bounded normalized offline JSON payload only against a server-owned approval containing provider, exact version, checksum, license URL and review receipt. It preserves attribution and declared modifications, checks official source hosts, retains original wording and produces exact/alias mapping proposals or ambiguity/unmapped states. The registry keeps immutable releases and permits explicit activation/rollback. No O*NET/ESCO release is installed or accepted in the product. See the [first-domain review pack](SOFTWARE_ENGINEERING_DOMAIN_PACK.md).

Market datasets require source/license/permission, geography, seniority, occupation version, dates, sample size, query version, bias/coverage report and review receipt, plus an exact server-owned approved hash. Missing, altered, future-dated or expired data disables frequency claims. This task performs no scraping or market collection.

`job_requirement_versions` and `job_requirements` are immutable, owner-scoped tables. The service-only save transaction derives ownership and JD source from the locked analysis/job, checks hash, exact requirement and importance citations, source-bound years, expected parent and idempotency, then writes the version, items and a metadata-only audit event together. Client and direct service writes are revoked. The bounded privacy export RPC reads both collections in one snapshot. Job/source/analysis/account deletion and retention remove derived records; active deletion revokes reads before cleanup.

Apply `20261012064727_job_requirement_versions.sql` before enabling this feature **and before running the updated privacy worker**, including with the feature flag off. Recovery is additive: disable the flag, retain immutable versions, and repair applied SQL with a new migration. Hosted deployment is deferred under the owner's localhost-first direction.
