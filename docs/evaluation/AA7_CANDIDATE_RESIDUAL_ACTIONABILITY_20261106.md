## The reported APT fix is outside the approved snapshot

The paired scanner reports `apt` and `libapt-pkg6.0` `2.6.1` affected by CVE-2026-109518, with fixed version `2.6.2`. [The actionability proof](AA7_FIXED_SNAPSHOT_APT_ACTIONABILITY_20261106.json) checks the actual approved repository set, rather than assuming the installed version is the newest available:

- The retained main arm64 package index is bound to the already signature-verified fixed-snapshot InRelease. Its SHA-256 is `2ddb1737692e8c45c53e8d57c0ce4cd21c78c5703b830c3226b1423566a06c00`. Both exact package stanzas are version `2.6.1`.
- The same requested `20261029T000000Z` Debian-security InRelease was retrieved and verified using the existing pinned worker image's Debian archive keyring. GPG verification returned exit 0, two valid signatures and no rejected signature status. No authentication or signature-expiry bypass was used.
- The security arm64 package index was fetched through its same-snapshot by-hash URL. Its 356,272 bytes match SHA-256 `330d9b021273d7911f3acd6a675b0181b3880e607420a00b56301d479a2652a8` from that signed InRelease. All 2,817 package stanzas were inspected; neither `apt` nor `libapt-pkg6.0` appears in that component.

Version `2.6.2` is therefore unavailable within the two authenticated snapshot components configured by this Dockerfile. An ordinary upgrade with those same pins cannot obtain the reported fix. Installing that fixed version requires a reviewed source/snapshot/backport decision; it must not silently move the date or repository. Removing unnecessary APT tooling from a separately reviewed final-runtime composition could instead remove those installed components, but that is a composition change requiring dependency and image revalidation, not a claim that `2.6.1` was patched. No such change was made here.
