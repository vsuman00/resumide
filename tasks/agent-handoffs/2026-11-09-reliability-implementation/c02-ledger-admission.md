# C02-S03A: concrete ledger and write admission protocol

Prepared 2026-11-09, Asia/Kolkata. **Source-backed design for coordinator review. No DDL, source change, migration application, service or hosted query ran.** This is the only new file in this leaf. It refines the frozen [storage proposal](c02-storage-contract.md), hash 8777cce5…, rather than changing its historical claims. The complete-prefix reader is now implemented at projection1.0.1; the earlier capped-query hypothesis was reproduced with a fake, not a measurement of the configured Supabase row cap. A08's five released files stay untouched pending peer review.

The selected protocol is an immutable normalized side ledger, one SQL transaction for each candidate action, and transaction-scoped owner advisory mutexes acquired before row locks. It covers old producers as well as new apply. The existing deployed Vercel caller and stopped deployment are material constraints: additive foundation and final write cutover are separate leaves. This document grants neither application nor cutover permission.

## 1. Exact authority and transaction boundary

The route follows existing `analysis.canonical.tsx`/`analysis.evidence.tsx`: authenticate with server-side `getAuthenticatedUser` (`auth.getUser`), same-origin check, server flag and private/no-store response. Pass that actor to a service-only SQL RPC; never accept an owner or organization supplied by the browser as authority. SQL resolves actual root/analysis/source ownership, current organization membership and active root after obtaining the mutex. For correction actions, actor must equal candidate owner; organization read membership alone does not authorize editing another candidate.

A correction action requires explicit review acknowledgement and an exact selected target/current-versus-proposed diff. That acknowledgement does not canonical-confirm the fact. Deterministic import/correction does not invent a dependency on `qualitative_ai` consent; actual AI calls retain their separate purpose/version consent checks. Consent writers join this protocol because a late upsert can recreate a deleted consent. Raw confirmations remain exact-source-candidate events; `correct_document_evidence` still requires candidate_id null for correct. No historical row is rewritten.

SQL checks the latest active attempt, source ID/checksum, evidence/extractor version (legacy extractor null), review max revision, assignment max revision and canonical expected head within the same transaction. Read DTOs and target IDs cannot grant this authority. A canonical head bound to a different evidence attempt is a source conflict; this leaf does not silently rebase its lineage. A reviewed new-source/rebase path remains A04 work.

## 2. Selected lock protocol, including existing producers

Define private `lock_candidate_owners(uuid[])` and a nonblocking claim variant. Derive every 64-bit advisory key **inside SQL only** as the signed first64bits of SHA256 over UTF8 `resumide:owner-write:v1:` plus lowercase UUID text. Deduplicate the actual bigint keys, sort them in signed numeric order, then acquire `pg_advisory_xact_lock` in that order. Retain the original distinct owner UUIDs separately for authority rechecks. Use the existing extensions.digest implementation; PostgreSQL converts the digest to bigint. No JavaScript lock-key implementation or session-level lock is used.

Sorting UUIDs alone is unsafe under a lossy key: A<B<C with key(A)=key(C)=X and key(B)=Y would make batches {A,B} acquire X,Y and {B,C} acquire Y,X. Sorting the unique actual resources prevents that inversion. After this ordering rule, collisions cause extra serialization but never shared authority. A private ordered-key acquisition helper can be exercised by operator-only isolated SQL tests with synthetic signed X/Y values; public RPCs always derive keys from real owned UUIDs. There is no production key override or test flag.

Every participating transaction follows:

1. Validate bounded scalar inputs and obtain candidate owner/root IDs by nonlocking reads; this read is not authorization. No `FOR UPDATE`, DML or producer call yet.
2. Acquire all unique owner mutex keys in signed numeric order. Never add another owner after acquiring any row lock. Re-read and validate immutable ownership/source relationships; abort if the frozen owner set changed.
3. Lock roots by UUID, then analyses by UUID, then immutable source/attempt rows as needed, then heads/queue/request/ledger rows in a fixed table-and-ID order. Recheck membership, active source, lease and deletion policy here. Nested producer calls reacquire only owner mutexes already held and use the same root/analysis order.
4. Publish normal candidate data only when no deletion request for the owner has status other than failed. Preserve the existing policy, including cancelled/completed deletion rows; do not silently change cancellation semantics. Privacy processing can update its own leased request/cleanup rows under the mutex after candidate access is revoked.
5. Commit or raise/roll back the entire SQL invocation. No provider, storage HTTP request or external rendering occurs while holding these locks.

The mutex is per owner, so deletion covers all owned resumes and future resume creation. New ingestion must acquire it before inserting its first jobs/resumes row. Locking only today's roots would leave a new-resume phantom.

**Global claims are explicit rewrites, not one-line guards.** `claim_analysis_job` currently dead-letters multiple owners before claiming a job (`20260911120000_phase7_queue_age_metric.sql:25–47`), and retention currently locks a multi-owner batch. Each rewritten claim first freezes a bounded candidate-ID/owner set with nonlocking reads. Acquire that complete derived unique key set in signed numeric order, using try-locks for claim availability; on any failed try-lock, return no work and end the transaction, releasing already obtained mutexes. Then lock and revalidate only those frozen IDs. Do not rescan and mutate new owners after locks. Preserve lease CAS, deadline, attempts, dead-letter outcomes and result shapes; bounded continuation handles later candidates. Retention likewise processes only its frozen owner/root/version set with the same derived-key ordering. A top-level empty-result RPC ends the transaction before another claim; transaction locks do not release merely because a nested function returns. No assumption that queues are empty is permitted. Set a first bounded policy of at most 1,024 frozen IDs/owners per transaction: analysis claim may inspect at most 1,000 expired IDs plus 16 eligible IDs, privacy claim at most 16 IDs, and retention retains its existing p_limit ceiling of 1,000. New IDs/owners after the snapshot wait for a later invocation. Runtime review must measure contention/fairness and test the candidate cap; a cap is not a permanent queue-size limit.

The existing initialize_privacy_request_steps and enqueue_analysis_job triggers are nested writers: their parent enqueue/ingestion RPC must already hold the complete key set. No row trigger acquires a new mutex after a producer's row locks. FK/source-validation and deferred ledger-integrity triggers may validate existing state while the producer already holds the mutex; they do not acquire owner barriers. Privileged operator writes, auth-account deletion and managed restore are outside application admission and require a maintenance/drain protocol. Full R19 auth erasure is not closed here.

`bootstrap_personal_workspace` runs inside the auth-user INSERT trigger. Its new-user-only public DML acquires the new owner's mutex first. The auth row already exists uncommitted in that transaction; ordinary producers cannot have a committed membership/data graph for that fresh UUID. Prove this fresh-user exception with registration-versus-ingestion tests, and prohibit UUID reuse/import while producers run. Do not generalize this exception to existing-owner triggers or auth DELETE.

## 4. Cross-language identity and replay

Choose `c02-command-bytes/1.0.0`, not JSON text equality/hashing across languages. Encode header ASCII `C02OP1` followed by LF. For each fixed-order atom, null is bytes `N;`; a non-null atom is `T` + ASCII decimal UTF8 byte length + `:` + UTF8 bytes + `;`. Length-prefix parsing preserves embedded delimiters. UUIDs are lowercase canonical text, SHA hex lowercase, integers base10 without signs/leading zeroes, booleans 0/1. Version/identifier strings use their exact stored Unicode; no trimming or Unicode normalization. Reject unpaired JavaScript surrogates. SQL uses convert_to/octet_length and JS uses Buffer.from/byteLength; both hash the identical bytes with SHA256.

The fixed order is kind, S, actor, evidence/extractor/target/projection/admission versions, expected review/assignment/head, review acknowledgement, selector count, then selectors in ascending `(event revision, field ordinal, assertion ID or explicit absent-slot marker, location kind, base version/fact/location IDs)` order. Each selector contains selected_assignment_id (null while assigning a newly allocated choice), event ID, target kind/assertion ID, mapping mode, exact existing placement or explicit add-placement specification, and optional prior assignment/application IDs for reassign/reapply. Reject duplicates before sorting. Field ordinals are fixed as name=0, email=1, phone=2, employer=3, role=4, dates=5, education=6, certification=7; location ordinals are contact=0, section=1, entry=2, bullet=3, new_entry=4, new_section_entry=5. These are codec-version constants, not locale collation. Reference/string sorting is bytewise UTF8; no SQL default collation or JavaScript localeCompare.

SQL rederives every semantic atom from owned stored rows and strict selectors, computes the authoritative hash, and stores normalized columns/ID selections. Compare both the hash and normalized typed values on replay; a supplied browser hash is diagnostic only. request_id, timestamps, newly generated child IDs and candidate values are not client identity inputs. Values come from the referenced immutable event. Exact replay returns its recorded final result before allocating new children and never moves the current head backward; a different expected head, selected target, assignment/application choice or admission version conflicts under that key. After access/deletion revocation, do not expose an old result merely because its idempotency key exists.

Initial import selectors use source assertion identity plus mapping_mode imported_assertion, not newly randomized fact/location IDs. The current importer uses randomUUID; SQL must uniquely resolve the generated raw fact by type and its exact full citation tuple after validating the original import body. An ambiguous mapping rejects. Existing-head actions bind exact fact/location IDs. Add selectors name an existing location or an explicitly reviewed new section/entry specification; server/SQL allocates the new technical IDs. An identical replay is independent of a regenerated preview's incidental IDs. No client-provided changed body bypasses the immutable-event/value and selected-delta checks.

## 5. Assignment, apply, add and lineage writes

Select service-only `assign_candidate_correction_targets` and `apply_candidate_corrections`, private `save_candidate_authored_fact` and `write_correction_snapshot`, and new `export_candidate_workspace_v2`. Privacy/direct-DML replacements are named `create_candidate_data_request`, `cancel_candidate_data_request`, `record_candidate_ai_consent`, `record_candidate_audit_event`, `record_candidate_ai_run` and `save_candidate_writer_draft`; these are proposed entrypoints with strict bounded schemas, not already available functions. Keep all old producer signatures unchanged. Select separate assign and apply actions. assign appends one or a bounded ordered batch of exact choices with review/assignment/head CAS and an operation receipt; it does not edit a canonical fact. Reassignment explicitly references the previous choice. Apply references committed assignment IDs and repeats all three CAS checks. A batch shares one owned source/analysis; it cannot retarget another owner's employer or select a source by value alone.

Resolve events to targets before latest-per-target selection. Confirm events target their exact source candidate and remain review-only. Legacy correct events have null candidate_id: unique target mapping is allowed; multiple choices require explicit selection; absent/unmapped import facts require reviewed add. An unresolved newer event for the field remains a blocker rather than being ignored in favor of an older resolved event. Assignment revisions are independent of review revision, so concurrent choices with unchanged raw corrections conflict correctly. Apply reads the actual SQL max revisions and current head; the A03 captured-prefix receipt alone is insufficient. For the first bounded implementation, review and assignment prefixes must each fit 1,000 rows, be complete/contiguous through the captured max, and be rechecked under the same locks. Larger histories return explicit continuation/unavailable; an indexed per-target proof is later scalable read-model work, not a silent truncation. Ancestor-origin proof stops at the matching gapless owned origin (maximum64 edges, reject known cycles), never demands an older root unnecessarily, and never matches by value alone. Commands allow 1–32 unique selectors, at most64KiB encoded selector bytes, each child at most the existing1MiB body bound, and8MiB aggregate child bodies. Check these before allocating child plans. These new-operation bounds are versioned internal work limits, not product-history limits.

For mapped apply, allocate the operation/child/application IDs inside the transaction. Insert provisional immutable operation/application rows with deferred result FKs, validate every server-built child against actual event/selection state, then call the unchanged strong canonical import/edit validators inside this one SQL invocation. Initial import creates the ordinary sourced/unconfirmed original, then selected clear-citation unconfirmed edit children. The wrapper raises if any nested result is non-applied, so no earlier child/receipt commits alone. The current authoring edit-then-confirm function is the source precedent; separate JS RPC calls are forbidden.

Every canonical producer must atomically call the private snapshot writer for a header and its complete active links. The snapshot writer has no public/service direct EXECUTE grant; only the validated definer producer can invoke it. Ordinary edit drops the edited fact's active link; unchanged facts inherit links only when exact fact identity/value agree. Confirm and rename retain valid links without inventing a new application. The correction wrapper's provisional application rows allow the new corrected child to link to its actual planned application before commit; deferred validation checks the result. Rollback/restore copies the selected historical snapshot links into the new child, including an explicit empty legacy snapshot when appropriate. It never overlays today's latest corrections. Any event previously applied requires explicit reapply referencing the prior application/current head after undo/manual changes, even under a fresh idempotency key.

**Add is selected as a separate validator, not hidden inside edit/import.** Admit a forward canonical-engine/1.0.2 producer for this operation only, with unchanged canonical JSON shape and retained /1.0.0–/1.0.1 readers. The old deployed strict reader does not accept /1.0.2; no such head may be produced until compatible readers are deployed. Historical dual read means the new reader accepts old versions, not that an old binary can read a new producer. Use existing change-event action create, target new fact, priorValue null; extend the SQL operation allowlist with add in its reviewed leaf. A private add validator permits exactly one event-derived typed unconfirmed fact with sources=[]/confirmation=null, exactly one selected contact/section/entry placement, and at most one explicitly reviewed new entry/section when absent. It preserves every unrelated fact/placement and validates section/field compatibility. Employer/date association requires an explicit target entry; no proximity inference. It cannot canonical-confirm, forge a citation or reuse an unrelated fact ID. New section title/type and entry creation are explicit reviewed selector inputs, not AI authority. This producer/admission change is not part of additive foundation or authorized for writing yet.
