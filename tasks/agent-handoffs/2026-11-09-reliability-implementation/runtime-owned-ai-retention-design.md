# Owned AI accounting retirement and 30-day disposition design

Source design only. No production source, profile, migration or test changed; no SQL was parsed or executed. [ADR-0020](../../../docs/decisions/0020-owned-ai-accounting-retention.md) accepts a maximum of 30 days from the first committed durable deletion-preparation event. Retries, settlement and restart cannot restart that clock. Root has resolved the expiry and restore choices below. They are implementation requirements, not verified behavior.

The [backend triage](</Users/vaibhavsuman/Development/Presonal Project/ResumeATS/resume_ats/tasks/agent-handoffs/2026-11-09-reliability-implementation/backend-owned-ai-privacy-lifecycle-triage.md>) matches the inspected source. `prepare_deletion_request(uuid,text)` persists `private.privacy_deletion_plans`, then deletes analyses, jobs, resumes, consents, memberships and profile. It does not delete Auth, organizations, audit rows or earlier export manifests. Its final definition is in `20260911130000_durable_privacy_deletion_plan.sql:73–133`. `complete_retention_item(uuid)` deletes a resume root only after all its recorded objects are deleted (`20260911110000_phase7_security_privacy_operations.sql:314–337`).

R03 operations, attempts and events retain restrictive Auth/org/pool relationships and immutable guards (`20261110062548_technical_ai_budget.sql:33–158`). A12 `canonical_rewrite_operations` and A13 operations/attempts have no cascading source/analysis FK; they survive ordinary content deletion. A13 publications do cascade with the actual analysis, original scoring input, source, run, Auth and organization. The published late-known guard currently depends on that erasable publication; backend's separately allocated forward repair removes that dependency. Counter `63ddc8a4` independently rejects a published operation whose publication is absent (`20261115082125_owned_ai_usage.sql:93–95`). Arbitrary missing publications must continue to fail closed.

1. **Implement the minimal content-retirement repair next.**

   Add the proposed private table `initial_feedback_content_retirements` with this exact initial row shape: `operation_id uuid PRIMARY KEY REFERENCES initial_feedback_operations(operation_id) ON DELETE RESTRICT`; `publication_id uuid NOT NULL UNIQUE`; nullable `attempt_id uuid` referencing the retained technical attempt; nullable `run_id uuid UNIQUE`; nonnull `owner_id`, `organization_id`, `analysis_id`, `resume_id`, `resume_version_id` UUIDs; `publication_state` restricted to `assessed|deterministic_only`; `binding_sha256` lowercase SHA256; `retired_at timestamptz`; nullable `deletion_request_id uuid` and `retention_item_id uuid`, with exactly one nonnull. Captured content-parent/request/item IDs are plain values, not cascading FKs. The proof must survive the authorized deletion and completion of its storage plan. It is linkable personal metadata, not anonymous data.

   There is one immutable proof per operation, no raw content, render, prompt, response, receipt or copied content hash. For an assessed publication, require its real attempt and run; deterministic-only requires no run. The capture helper derives every field from the locked existing publication, operation and attempt, and validates any actual run against owner/org/analysis, model, prompt, input binding and exact known usage. It cannot manufacture a proof from an already-missing publication. Historical repair is allowed only while the original rows still exist and pass those checks.

   Proposed capture signature is `private.retire_initial_feedback_publications(p_owner_id uuid,p_resume_id uuid,p_deletion_request_id uuid,p_retention_item_id uuid) -> void`; account deletion has null resume selector, while root retention requires the actual resume. Guarded forward replacements of the two actual deletion producers call it immediately before their parent DELETE. Account deletion must prove its leased processing deletion request and committed-in-the-same-transaction durable storage plan. Root retention must prove the actual item/root and the existing all-items-deleted condition. No client reason, support Boolean, custom GUC or arbitrary DELETE creates retirement authority. Acquire the existing exclusive owner barrier before object rows where possible. After an existing request/item lock, use nonblocking owner and source locks and abort/retry on conflict. Within the content graph use source/root → analysis → operation → attempt → publication → run; do not wait for a reverse-order lock.

   The counter successor keeps the one-statement snapshot and all-month link validation. A missing publication is acceptable only when an exact immutable retirement matches the retained operation's publication ID, owner/org/analysis, binding and attempt. If a linked legacy run survives, validate its full existing tuple and usage before excluding that exact ID. The retirement is neither another usage component nor permission to charge twice. Present publication/proof conflicts, a mismatched proof, or absence of both publication and proof still refuse the whole read. The actual attempt remains the usage/claim-month authority, including late known fill after content removal.

   Add a separate proposed `export_owned_ai_retirement_records(p_user_id uuid) -> jsonb`, returning strict `{schemaVersion:'owned-ai-retirement-export/1.0.0',retirements:[all owned rows]}` across organizations, periods and flags. Reuse the existing A13 4096-row/32MiB whole-reply bounds, failing rather than truncating. Keep the current A13 export shape unchanged. This new export is explicitly denied by default; its effective service EXECUTE must have its own metadata capability, not be inferred from the existing `exportExecutable` field. The later privacy adapter must require it unconditionally.

   Keep the existing 19-key/11-string full feedback metadata/profile shape. Renew only the real changed usage/checker/metadata source pins; extend the finite checker manifest over the new table, capture/export routines and exact deletion-producer postimages. Proposed `read_owned_ai_retirement_readiness()` has eight keys: `schemaVersion:'owned-ai-retirement-readiness/1.0.0'`, `profileVersion:'owned-ai-retirement-profile/1.0.0'`, `schemaReady`, `exportExecutable`, `checkerSha256`, `captureSha256`, `exportSha256`, `metadataSha256`. Export a separate six-string `OWNED_AI_RETIREMENT_PROFILE` alongside the unchanged full-profile shape, using actual bodies only. Compute metadata hashes from catalogs; externally pin the checker and metadata after bodies exist. Neither checker embeds its own expected hash. Default ACLs deny all new data/helpers, including service; only metadata may be service-readable. Existing CHECK/default reconciliation and Native/adoption holds remain.

   The next bounded implementation is five files: one actual CLI forward migration after backend's late-known repair, the transferred full feedback profile successor, one text/source-contract test, one deferred rollback-only verifier and a handoff. No old migration changes. The verifier must retire a genuinely published row through each actual deletion producer, preserve late known usage, keep usage totals unchanged, reject forged/missing retirement and verify owner-wide export. It remains unexecuted until separately admitted. Full expiry, Auth and restore are a later leaf.

2. **Record the immutable deadline before erasing content.**

   The later lifecycle migration needs a private `owned_ai_deletion_dispositions` row with `owner_id uuid PRIMARY KEY`, `first_request_id uuid`, `prepared_at timestamptz`, `expires_at timestamptz`, and a closed processing phase. No organization-specific key may split an owner's account-deletion clock. Insert it in the same transaction as the first durable account deletion plan, before candidate DELETE; take one DB-clock value and derive expiry as exactly 720 hours. An exact retry reads the same row. No update may move either timestamp later. It is not dependent on `privacy_deletion_plans`, which completion currently deletes. A failed worker must not make prepared deletion inactive or restore access merely because `data_requests.status` becomes failed.

   Automatic source retirement uses its real durable retention-item event for the affected operation's maximum deadline; a later account disposition can shorten, never extend it. The existing owner/write barrier must eventually also deny a prepared disposition, independently of request retry status. That forward body change requires renewal of every actually affected source manifest, not edits to frozen migrations or a claim that today's base138 already accepts it. Until paired adoption, the new staged stores remain denied.

3. **Expire identity atomically, retaining only unlinked safety totals.**

   Proposed private `expire_owned_ai_disposition(p_owner_id uuid) -> jsonb` is an operator/worker function, denied until paired adoption. It locks the due disposition and exact accounting closure, folds known usage into original UTC-month aggregates, installs required safety blocks, deletes the identified rows, and deletes the disposition/proofs in one transaction. Missing work is `not_pending`, not an erasure certificate. An ambiguous transaction is retried; rollback cannot partially credit aggregates. Deleting only Auth or changing FKs to CASCADE is insufficient.

   The purge covers R03 user operations, attempts and events; A12 operations; A13 operations/attempts/retirements; their request, binding, plan, receipt, policy-selection, worker/lease, reconciliation, actor/evidence and linkage material. Remove all subject/operation/attempt/run IDs, payload/evidence hashes and exact claim/update timestamps from the retained disposition output. Include Auth/org FK reconnectors and subject-bearing opening/reconciliation evidence. Other users' live rows are not erased merely because they share an organization. Immutable guards need exact relational disposition authority, not a general bypass Boolean. Shared pool/opening projections need a reviewed rebuild from remaining authorized state; they cannot retain a deleted subject's attributable evidence or silently free capacity.

   Proposed restricted aggregate rows are keyed only by original UTC month, with numeric shared-quota known tokens, separately labeled R03 spent tokens/cost, unresolved count and reserved exposure. No owner/org, operation, attempt, deletion batch, model/policy hash or per-subject receipt survives. Shared-quota tokens use the validated legacy/A12/A13 partition once; R03 cost is not a second debit, and its overlapping token total is never added to that partition. Aggregate reporting must preserve that distinction.

   At expiry exact per-attempt settlement/reconciliation closes permanently. Late evidence cannot recreate the erased identity. Unknown exposure remains blocked until controlled aggregate reconciliation; retention expiry never implies zero usage, release or refund. Root selected a global safety block when org attribution must be removed. For a 31-day current-month edge, preserve the known amount in the original-period aggregate and block execution globally through that period's UTC end. Unresolved exposure continues its conservative technical hold. Callers receive only fixed unavailable/blocked outcomes, never another organization's global totals. This changes quota disposition and requires its own reviewed R03/current-caller closure before activation.

4. **Pair exports, artifacts, Auth and restore with lifecycle adoption.**

   Current `privacy-worker.ts:255–428` requires A12/workspace/original-scoring exports but omits R03 and A13 technical collections. Its request listing omits earlier `result_manifest` content; those manifests remain personal copies. The paired worker must export every retained owned R03 operation/attempt/event and subject-bearing reconciliation/opening record, A12 row, A13 operation/attempt/publication, retirement and disposition across all organizations and feature flags. Require strict per-row owner/parent checks and bounded complete replies; missing/denied/schema drift is a failed export, never `[]`. Do not export other owners' shared pool histories merely to expose this owner's contribution.

   At preparation, invalidate prior export downloads and durably capture exact old artifact/object keys before clearing old manifests. Erase inline `data_requests.result_manifest` copies, storage artifacts and retry plans; a successful flag is not physical deletion proof. Revoke Auth sessions and prevent new account work immediately after durable preparation. Actual Auth deletion, personal-organization erasure/ownership transfer and remaining audit/data-request cleanup follow only after restrictive ledger relationships are disposed. They are not performed by today's content/profile RPC. External object/Auth failures must be resolved within the maximum period; failure is a retention breach/adoption blocker, not permission to extend identifiers indefinitely.

   The current synthetic restore verifier checks manifest checksums and ownership only; it has no deletion replay. Within 30 days, restore into quarantine, replay the actual retained disposition journal before serving, and keep all sessions/dispatch disabled. At purge, atomically advance an owner-free minimum eligible snapshot watermark. A restore older than that floor is refused once per-owner replay material has expired. Restore authority must obtain the monotonic floor from a control plane not rolled back with the candidate snapshot. No perpetual owner/hash tombstone is retained. Provider backup/object expiry and an actual isolated restore drill remain hosted holds.

Root accepted the minimal retirement contract and the conservative expiry/restore choices; implementation allocations, exact postimages, Native locks/cascades/rollback/ACL, physical deletion, scheduling and release acceptance remain separate.
