# CR-U03: exact-value confirmation and draft recovery

CR-U03 is **PARTIAL**. Three local source/application slices are **VERIFIED**; native browser, managed storage/concurrency and full consumer acceptance remain open. This work closes the affected source repair, not the entire reliability plan or a release gate.

## Result

Clarification now uses two native POST steps. The first derives and displays the complete fact from the owned immutable base and the candidate answer without writing. The final form requires explicit review and carries the original target, version, answer and key plus a digest of the complete displayed value. The server derives the same value before accepting a new clarification. This digest binds content equality; it does not prove that a person read the page. An existing owned exact receipt remains replayable without new proof. The SQL command, request-size limits, source ownership and fresh-head checks remain unchanged.

Acknowledgements reset when their exact value, source, target, version or persisted history context changes. Current confirmation uses the current saved fact, while a failed request retains its original retry command. Multiline before/after values preserve their visual whitespace. Confirmation remains a candidate declaration; it does not supply extracted citations, calibrate OCR or unlock authoritative scores.

A rejected canonical fact edit or section rename retains the authenticated, strictly parsed command. Its exact retry keeps the original version, target, value and key. A separate native form displays the current saved value and requires a new acknowledgement before attempting the retained change against the current head with a fresh key. Historical views and missing targets keep the draft readable without selecting a substitute target. Invalid or unauthenticated form bodies are not reflected.

Client data revalidation previously cleared action data and lost the retained draft. The first repair kept one draft in page memory, but source review and two actual Router regressions found that an unrelated success erased it and another target's rejection replaced it. The follow-up retains parsed commands separately by target under the same analysis, resume, source and owner binding. An unrelated action preserves other drafts; only matching operation/target/value success resolves its own draft. Each current target gets a distinct server-generated retry key. A source change clears the collection. The draft is not put in local storage or a URL. Reloading or leaving the page can still discard that temporary memory, as the recovery panel explains.
