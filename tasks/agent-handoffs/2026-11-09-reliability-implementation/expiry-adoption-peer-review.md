The proposals support two bounded next slices: repair the actual stale-export producer, and implement the independent floor/controller with explicit unavailable production adapters. Neither supplies a usable adopter. No further general review of the frozen conservation core is needed.

Four contract boundaries need explicit treatment before dependent implementation or activation:

1. **Preserve first clocks through restore, not only final erasure.** Account preparation at T0 followed by restoration of a valid T-1 backup at T+15 days can remove the first clock and durable barrier before any expiry fold advances the floor. Integrate the independent prospective generation/checkpoint protocol with first durable account preparation and first root retention/tombstone capture as well as final fold, or supply another real authority that rejects every such older restore. A rollbackable export-generation bump does not preserve the original 720-hour deadline. This is required later integration, not an addition to the proposed first five-file store slice.
2. **Bind export completion to the actual claim.** `privacy-worker.ts` builds a manifest outside completion; `complete_privacy_request` stores `p_manifest` using only request ID, processing state and worker ID. The `serialize_deletion_request` trigger takes the candidate write barrier, but root retirement leaves the account active. A pre-fold manifest can therefore be stored afterward. The proposed hidden generation and shared/exclusive global gate close that race only when claim attempt and live lease are also required: same-worker reclaim could otherwise restamp the row while its old asynchronous build survives. The existing `attempt_count`, returned as `attempt`, supplies an actual fence. The backend proposal now includes it for prepare/complete/fail, rejects old or unstamped work and denies forged authority columns. Preserve that correction. A stale manifest must be discarded and rebuilt, never relabelled under a new claim. Freeze the old-signature refusal and Node consumer changes together.
3. **Keep pre-fold authorization distinct from post-fold finalization.** R03 operations/operators and A12 operations have restrictive Auth/org FKs. Requiring Auth/org absence before ledger removal is circular. The proposal correctly uses actual pre-fold quarantine, then a separately pinned finish callback after accounting removal and before disposition/work removal. Capture root/version/cause/first-clock scope transiently before removing it. Finish failure must roll back the relational fold. Account scope needs FK-safe Auth/org and request/audit cleanup; root scope preserves Auth, profile, memberships and unrelated roots. Managed Auth transactional capability is unverified; an API-only delete after commit cannot satisfy this atomic contract. Do not replace that missing capability with a Boolean, echo witness or invented grant.
4. **Define recovery outcomes without a personal journal.** Before destructive work, durably quarantine, obtain real ingress/writer fencing, and advance the independent floor. Committed outcome permits reconciliation of that exact generation; proven non-commit can start a new fenced transition at a higher generation; unknown outcome permits neither retry nor ready publication. Never lower/reuse a generation or infer commit from counts. Define a generation as the global DB-instance/cutover boundary, not an owner set that requires a retained subject hash or receipt. Current CAS revision/token and trusted DB checkpoint/fence proof must reject delayed controllers. This clarification was requested from runtime.

The runtime filesystem proposal states its operational limits honestly: it cannot detect replacement of its authority volume by a valid older copy. Real independence, actual host-topology locking, external ingress/writer fencing and authentic backup/checkpoint provenance remain mandatory before adoption. Its journal permits only global protocol/generation/revision/phase, without subject IDs, selectors, hashes, timestamps or per-subject receipts. Startup/readyz checks alone cannot fence existing workers, direct Native connections, Auth/Data API/Storage exposure or snapshots predating new DB guards. Missing proof keeps admission unavailable; no safe backup means an availability failure, not permission to resurrect deleted selectors.

The backend actor/opening proposals also retain necessary distinctions. Actor sanitization must preserve a surviving foreign owner's exact charge/reconciliation state while removing the deleted actor's event/evidence references, and invalidate affected stored exports as well as in-flight ones. Its marker remains that foreign owner's technical metadata, not anonymous data, and must disappear when that attempt expires. Pure-org opening removal must conserve opening balances and remaining over-limit fences before deleting the rows that provide dedup. Shared/transferred organizations and immutable foreign authoring evidence need actual accepted contracts or must block account finish; no transfer policy or historical attribution may be guessed.
