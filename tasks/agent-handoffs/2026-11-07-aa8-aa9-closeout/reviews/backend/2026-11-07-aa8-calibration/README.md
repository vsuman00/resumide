# AA083 offline calibration proposals

Owned source: `app/lib/server/evaluation-calibration.ts` and its focused unit tests. Uses the integrated annotation/partition APIs without modifying the corpus, annotation, partition or AA4 policy. The worktree copy of the integrated partition module is a dependency baseline, not a new integration diff.

`proposeEvaluationCalibration(input, reader, authority?)` reads labels only through `readEvaluationPartitionLabels` with purpose `calibration`. Development and calibration partitions are allowed; locked-test access is denied before the reader. The immutable lock is checked again after the asynchronous reader. Returned observations must bind the exact requested source IDs/hashes; duplicates, foreign rows, raw fields and feature drift fail closed.

The caller supplies at most 48 versioned candidates across the three existing AA4 dimensions. Each candidate declares at most 16 positive feature weights, a threshold and a coverage parameter. Candidates within one dimension must use the same feature set. Fully known features use the declared total weight once; any missing/null applicable feature or explicit withholding withholds the prediction regardless of a lower coverage parameter. Known zero remains evaluated zero. No not-applicable inference or missing-weight renormalization exists.

Each dimension is selected separately. There is no combined ATS/job score. The fixed schema-1 selection loss is the mean of normalized absolute score error and threshold classification error. Every missing observation, reference or withheld prediction contributes worst loss 1 in the full requested-source denominator. Reports retain evaluated/missing/withheld/reference-missing counts, coverage, conditional score/classification errors, penalized loss, candidate sensitivity and explicit rejection reasons. Equal losses prefer higher coverage, then version order. No evaluated pair means no selected policy for that dimension and an insufficient proposal.

A ready proposal is a computable offline proposal, not a performance, calibration or release approval. Hashes bind normalized candidates, actual supplied observations, verified lock, rationale and rollback policy version. The existing AA4 draft policy ID is accepted as the rollback version and remains unchanged. Synthetic engineering can produce proposals. Future representative calibration additionally requires the upstream independently authorized human/partition path and a separate trusted exact-proposal authorization callback. Missing/throwing/rejecting authority denies that eligibility. Production adoption is always forbidden by this function.

Actual checks: 12 focused behavioral tests pass under Node.js 22.23.4 with private verification mode. Tests cover real candidate/threshold selection, sensitivity, locked/denied/drift no-read behavior, post-read drift, missing high-weight versus known-zero input, missing rows/references/withheld cases, feature-dropping rejection, deterministic ordering, development-only input, future trusted authority and sanitized reader failure. No DB, provider, service, AA7 checks or production scoring change occurred. Focused TypeScript, lint and formatting are recorded in the manifest; integrated review/checks belong to the coordinator.
