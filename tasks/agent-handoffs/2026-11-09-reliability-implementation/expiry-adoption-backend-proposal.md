## Next bounded slice: close the real export resurrection path

An active account can build an export before its root expires and call `complete_privacy_request` afterward. Clearing stored manifests inside the fold alone cannot stop this later stale write. `buildExportManifest` spans several RPC/REST reads outside completion. `api.privacy-export.ts` now checks durable account access before and after loading a manifest, but root retirement leaves that account active.

Implement an owner-free global export generation and trusted per-claim completion fence, paired with actual old-manifest removal. This does real work through existing producers and does not require a fabricated adopter:

1. Add a metadata-only singleton generation with no owner/org/time/hash. Root fold takes its existing exclusive global gate, advances generation in the same transaction and clears all stored inline export manifests belonging to that root's owner before personal accounting removal. First durable account preparation similarly advances generation and clears that owner's old inline copies. Never reset generation on retry or infer an epoch for old work. This is a stale-producer fence, not the independent restore floor.
2. `claim_privacy_request(worker,lease)` records the current generation in a protected column for an export claim. Its existing `attempt_count` increments monotonically and is already returned as `attempt` and retained by `PrivacyRequestSchema`. Use that actual attempt; worker ID alone is insufficient if the same long-lived worker reclaims an expired request.
3. Add explicit fenced successor signatures for prepare, complete and fail: require request ID, worker ID, existing returned attempt, and a live lease; complete also requires the row's claimed generation to equal the current generation under the shared global gate. No caller-supplied epoch is authority. Unsafe old signatures must refuse rather than silently complete old/unstamped work. Complete/fail from attempt N cannot mutate attempt N+1, even with the same worker ID. Prepare also needs that fence to close stale deletion-worker writes.
4. Prevent direct service INSERT/UPDATE of generation, attempt and lease authority. Current server inserts only `id,organization_id,user_id,kind,status` and directly updates only `status` for queued cancellation (`privacy.ts`). Preserve those needed column privileges; revoke broad write privileges that would let a service caller forge protected fields. Definer claim/complete functions perform the protected writes. Verify actual ACL closure rather than assuming RLS restricts service role.
5. A stale completion returns failure and discards its built manifest; it must not relabel/reuse that manifest under a fresh claim. A new claim rebuilds. Old completed unrelated-owner exports need not disappear on a root fold; their in-flight producers may conservatively fail a global generation comparison.

Propose the first backend author allocation as exactly five files: one CLI-created forward migration, `app/lib/server/owned-ai-expiry-profile.ts`, new `tests/unit/privacy-export-generation-sql.test.ts`, new `scripts/verify-privacy-export-generation.sql` (deferred rollback draft), and a leaf handoff. This is a core authoring slice; its dependent pin successors are mandatory before integration: `initial-feedback-profile.ts` (including retirement profile), `owned-legacy-ai-usage-profile.ts`, `ai-budget-source-profile.ts`, and `owned-ai-disposition-profile.ts`. Actual current hashes show preparation reaches retirement/disposition/usage checkers, while fold reaches expiry safety then source/usage/disposition/main readiness. No scoring policy renewal is needed. Put those four files in a separate ordered allocation; never publish guessed pins.

Pair a separate Node allocation for `privacy-worker.ts` and its exact affected fixtures to pass the already available attempt to successor RPCs and prove the same-worker reclaim race, expired lease, unstamped claim, old signature, generation advance, stale manifest refusal and successful rebuilt export. Current public export JSON need not change; privacy mutation RPC arguments explicitly do. The source five-file core alone is not the complete consumer adoption.

## Required pre-fold verifier versus post-fold finish

The verifier cannot require `auth.users` or owned organizations already absent. R03 operations and reconciliation operators, A12 operations, A13 operations and policy selections have restrictive Auth/org relationships. Auth deletion first can fail; its organization-owner CASCADE can also remove another person's content. Conversely, current fold removes the account disposition/work before there is any finish hook. An external Auth API call after that commit can fail after the only disposition journal has gone.

Freeze an explicit paired protocol:

- Pre-fold verification proves durable account non-admission, actual session/credential quarantine, object/export closure and independent current-generation/floor authority. It proves which organization and actor cleanup will be safe; it does not require prematurely deleted FK parents. Root scope does not revoke the active account or its unrelated roots.
- Preserve a strict transient complete cleanup scope before deleting accounting. Current work identity has only analysis/operation/run selectors; after deletion the finish step cannot recover root/version/first-request/item relationships. Add the actual immutable root/source/cause/first-clock mapping to a private scope successor or a local transient scope value derived under the same locks. Do not guess it from owner/hash after deletion or retain another permanent receipt.
- Add a separately pinned private finish callback after fold/removal but before account disposition/work removal. It performs the allowed DB cleanup and verifies no selected personal survivors; failure rolls back aggregates and removal. Approval must pin both actual verifier and finish bodies/properties/ACLs. Current capability schema admits only the verifier signature, so its closed seal needs an explicit forward successor, not an automatic learned digest.
- Account finish must remove its exact remaining request/step/plan/item/audit and allowed organization/Auth dependencies in FK order. Root finish removes only selected root copies/plans/items and stale exports, leaving Auth, membership, profile, unrelated organization data and other roots intact.

Managed Auth/session internals and transactional deletion capability are not established by this repository. Existing `getAuthenticatedUser` reads Auth; fixture-only `auth.admin.deleteUser` calls do not supply a production cleanup protocol. If only an out-of-transaction Auth API is available, a pre-fold Boolean cannot make post-commit Auth deletion atomic or meet the maximum period. The actual managed-schema/adapter contract and postconditions must be implemented and verified before approval; do not invent an Auth-superuser grant. Account cleanup stays unavailable until that dependency is real.

The [runtime restore proposal](expiry-adoption-runtime-proposal.md) supplies the required independent quarantine/floor direction. Pair its committed DB-instance generation/checkpoint in the fold transaction and its actual trusted current-fence bridge before approving either callback. The existing `p_limit` sweep argument, echo witness, candidate snapshot timestamp or database-only generation cannot establish that authority. Unknown outcomes stay quarantined; no blind fold retry or floor rollback.

## Foreign actors: preserve the foreign spend, remove this actor

Current `ai_budget_events(kind='reconcile')` requires actor, reconciliation ID and evidence hash; events reject mutation/deletion. Nulling the actor is not legal. The actual unsolved case is this account acting on another owner's surviving attempt. An owned operation's event may be removed with that operation after conservation even when its operator was somebody else.

Proposed follow-on schema: a private marker keyed only by the surviving foreign attempt, recording reconciled state without the erased actor, old event/reconciliation IDs, evidence/approval hash or exact actor-action time. This remains technical metadata attributable to the foreign owner, not an anonymous aggregate. Under locked account-disposition authority, atomically install that marker, remove the original actor-bearing event and revoke/delete this actor's reconciliation-operator rows. Do not alter the foreign attempt state, actual usage/cost, period or pool balances.

Three real consumers need the same successor: `ai_budget_blocked` must recognize the surviving reconciliation; `ai_budget_transition` must refuse a new reconciliation that would recreate it or change known spend; `export_owned_ai_budget_records` plus its strict Node reader must represent sanitized history explicitly. A fake replacement old receipt or manufactured original event time is unacceptable. Freeze an export successor before writing this transition. Export that marker only as the surviving foreign owner's technical state, and remove it when that foreign attempt itself expires; the current core must adopt that child deletion too. Preserve positive/overage/unknown history validation; the foreign owner's charge must neither repeat nor become blocked merely because its original actor was erased.

Account actor sanitization can invalidate cached foreign-owner manifests that contain old event/evidence identifiers. The generation fence handles in-flight copies; clear affected stored manifests from a proved inventory or conservatively invalidate all server-held exports for that transition. Clearing only the deleted actor's manifests is insufficient. Do not conflate this with deleting another owner's spend.

Auth CASCADE also reaches `audit_events.actor_id`, `evidence_corrections.actor_id` and `change_events.actor_id`. Thus R03 sanitization alone does not certify the full foreign-actor closure: foreign immutable authoring evidence/events and embedded actor references need their own accepted transition or must block account finish. Source inspection establishes those FK hazards; it does not establish that production contains such rows.

## Opening/pool and organization finish

The core rebuilds pools but deliberately retains openings, their evidence hash, organization key and creation time. It folds selected R03 attempts, not opening balances. These retained rows can block organization deletion and may reconnect the subject. An export omission label is not proof that evidence is non-personal.

For a proved wholly owned organization with no foreign content, ledger, membership or other surviving ownership, finish can fold the remaining opening's tokens/cost once into its actual original opening period, separately from shared quota, then delete empty pools and openings in FK order. If an opening-only pool still exceeds its limit, transfer that fence to `unresolved_pool_deficits` before removing it. The core's earlier overlimit-to-not-overlimit transition does not cover deleting an opening-only still-overlimit pool. Deleting the actual opening row in that same transaction supplies retry dedup; no personal marker survives.

Never attribute part of a shared opening by owner/hash, proportionally split its cost, replace evidence with a constant claiming anonymity, or blindly cascade an organization with other owners' records. Shared/formerly transferred organizations require an actual ownership/transfer/evidence-disposition contract; absent one, refuse and report the deadline failure. No enterprise transfer policy is selected here.

`data_requests.result_manifest` is an actual inline copy, `privacy_request_steps` and `privacy_deletion_plans` cascade from requests, and retention items retain exact storage keys. Validate/capture actual cleanup keys and first-clock dependencies before clearing/deleting them. Legacy-run validation still uses those cause rows, so finish must run after accounting validation/removal, not before. Physical object success, signed URL/session closure and provider backup behavior remain external evidence requirements, not consequences of SQL row deletion.

This ordering supplies real export safety next, followed by actor/opening transitions and a real verifier/finish bridge. It leaves no plan to keep the fold permanently denied, and makes no claim that these unimplemented pieces or the live 720-hour guarantee already work.
