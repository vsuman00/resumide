## Concrete source findings

1. **Account preparation has a durable plan, but no durable expiry disposition.** The current `public.prepare_deletion_request(uuid,text)` in `supabase/migrations/20261115100607_owned_ai_retirement.sql:172` locks the leased deletion request, creates/reuses `private.privacy_deletion_plans`, captures A13 publications, then deletes candidate content/profile/memberships. Its returned `databaseDeletedAt` is a fresh response timestamp, not an immutable start. `public.complete_privacy_request(uuid,text,jsonb)` in `20260911130000_durable_privacy_deletion_plan.sql:135` deletes the storage plan. Neither RPC deletes Auth or organizations. Store first preparation independently of both the plan and request cascade; a response timestamp or completed request is insufficient.

2. **Automatic retirement begins before final object completion.** `public.claim_expired_resume_objects(timestamptz,integer)` in `20260911130000_durable_privacy_deletion_plan.sql:15` inserts/requeues `private.retention_items` and marks the selected root deleted in one transaction. Existing `created_at` survives conflict retry; `attempt_count`, status and eventual `completed_at` change. `public.complete_retention_item(uuid)` in `20261115100607_owned_ai_retirement.sql:228` captures only published A13 rows once all objects report deleted, then deletes the root. Starting the expiry at this completion would extend retention when storage deletion fails. Capture the operation closure and first clock at the first committed retirement claim, while source relationships exist. Published A13 proof may still be captured at final deletion under its current stricter authority.

3. **A13 publication retirements do not cover every retained operation.** `initial_feedback_content_retirements` has `retired_at`, request/item selectors and linkable binding/source IDs, but no deadline. The capture helper filters operations with nonnull `publication_id`. Unpublished A13 operations/attempts and A12 rows survive content deletion too. A12 has `owner_id`, `analysis_id`, `source_id`, request/policy/receipt JSON, `run_id`, binding/plan hashes and claim time (`20261114181344_canonical_rewrite_operations.sql:10`). A13 has explicit resume/version IDs, binding JSON, worker lease, usage and `budget_attempt_id` (`20261115072701_initial_feedback_operations.sql:136`). Capture their actual rows before parents disappear; do not derive a missing publication proof or reset a previously captured clock.

4. **R03 lacks a general source-to-operation relation.** `private.ai_budget_operations` has owner/org/surface/payload/binding metadata, but no analysis/resume/source column (`20261110062548_technical_ai_budget.sql:60`). A12 uses the same operation ID and binding hash in its budget request; A13 validates its operation/attempt and records `budget_attempt_id`. Legacy qualitative uses `analysisId` as operation ID (`app/lib/server/qualitative-stage.ts:195`). Legacy rewrite and Build derive an ID from owner/org/surface/client nonce (`rewrite-service.ts:317`, `build-assist-service.ts:276`, `ai-budget-attempt.ts:25`); these IDs cannot be decoded into a root. Build is standalone and has no persisted resume root to infer. Account deletion can select every R03 row by `user_id`. Per-resume retirement cannot safely select all R03 rows by owner or guess from a payload hash. A mandatory source-registration/admission contract, plus an explicit historical unbound-operation policy, is missing. Classifying standalone Build under one retired resume is unsupported by the current contract.

5. **A failed request can reopen the existing barrier.** `private.candidate_write_blocked(uuid)` ignores failed/cancelled requests (`20261110085512_privacy_write_barrier.sql:8`); server `filterBlockingDeletions` and `api.privacy-export.ts` use the same distinction. That behavior is valid before preparation but insufficient after irrevocable preparation. Add the durable disposition predicate to the DB barrier and server access contract. Cancellation/failure bookkeeping must never cancel a prepared disposition. The barrier patch already covers R03 reserve/claim and reserve-next; preserve those actual call sites and fresh owner-lock visibility.

6. **Deleting selectors would currently weaken once-dispatch.** A12 `canonical_rewrite_owner(uuid,uuid)` and A13's preparation/claim paths recheck live analysis/source, active root, membership and privacy admission. Missing retired sources therefore prevent these APIs recreating old work. R03 `private.ai_budget_transition(uuid,uuid,jsonb,text)` and `public.ai_budget_reserve_next(uuid,uuid,jsonb)` require owner/membership/privacy admission but no live source. Once its operation row is erased, an active owner can submit an old generic operation ID as new. Deterministic UUID generation alone does not stop that. Before purge activation, make source-backed R03 admission validate a server-owned immutable parent and an operation identity tied to that parent, remove generic rebinding access, and prevent restoration/recreation of the old parent. Standalone Build needs its own retired request lifecycle/identity contract. Do not preserve a perpetual subject/hash tombstone to conceal this gap. Account deletion additionally needs confirmed Auth removal, session denial and no re-import of the deleted Auth UUID; profile deletion alone does not provide them.

7. **Actor closure differs from operation ownership.** R03 reconciliation events can reference this subject as `operator_id` on another owner's attempt. `ai_budget_reconciliation_operators` retains `approval_sha256`; events retain `reconciliation_id` and `evidence_sha256`; period openings retain `evidence_sha256`. Operations/events/openings reject deletion through `ai_budget_immutable()`. A13 operation/attempt/retirement guards reject deletion too. An account purge must capture both owned-operation closure and foreign-operation actor closure. Never purge the foreign operation or refund its known spend. Current reconciliation CHECK requires nonnull actor/evidence, so nulling the actor is not an implementable patch. A forward relationally authorized de-identification transition must replace that subject-bearing reconciliation history while preserving the foreign attempt's reconciled/blocked meaning. Its sanitized representation is an explicit missing schema/API contract, not an existing field. Opening evidence has no subject attribution column; an omission label does not prove the evidence cannot reconnect a person.

8. **Export is now paired, but old copies and future dispositions are absent.** The accepted design's older export-omission observation is historical: `privacy-worker.ts:118` now unconditionally obtains R03 plus paired A13/retirement exports and preserves nine AI collections and redaction metadata. `export_owned_ai_budget_records(uuid)` deliberately distinguishes owned events from own actor actions on foreign operations (`20261115102625_owned_ai_budget_export.sql:94`). Retain those bounds/ownership checks. Current `data_requests` export projection omits earlier `result_manifest`; preparation does not clear those inline copies. The download route serves the stored manifest after request-status checks. Capture and invalidate old manifests and actual storage keys durably before clearing them. Current stored exports are inline JSON; do not invent an export-artifact table. Existing resume object keys live in versions/plans/retention items and exported file lists. Keep exact keys only in a bounded cleanup plan until physical deletion, then erase that plan and request/actor/evidence references by deadline.

9. **Auth/org and restore are adoption blockers.** Auth `getUser()` (`app/lib/server/auth.ts`) is a reader, not deletion/session revocation. Organization owner FK cascades from Auth (`20260909073321_candidate_resume_analysis.sql:24`), while R03/A12/A13 use restrictive Auth/org FKs. Blind Auth deletion can fail or remove other owners' org content. Resolve personal-org deletion versus transfer from actual membership/content state; no enterprise-wide deletion is inferred. `verifyRestoredSnapshot` in `backup-restore.ts` and `scripts/verify-restore.ts` check checksum/ownership only. The restore runbook has no disposition replay or external monotonic floor. These are required source additions, followed by separately authorized real acceptance.

## Next bounded implementation

Implement **clock and closure capture first**, in one forward migration after the current export/retirement sources, plus its separate readiness/profile, strict export adapter/worker addition, source-contract tests, deferred rollback-only native verifier and handoff. Keep expiry mutators denied. Do not edit old migrations or spend the current worker allocations on this leaf.

- Add the accepted proposed `private.owned_ai_deletion_dispositions` account row: owner key, first request, one DB-clock `prepared_at`, exact `prepared_at + interval '720 hours'` expiry and closed phase. Create/reuse it in the same transaction as the first durable plan, before candidate deletion. No Auth/request FK cascade may erase it prematurely. Retried/late settlement paths cannot update either clock; an earlier per-operation deadline wins.
- Add a separate proposed operation-disposition relation for typed R03/A12/A13 selectors, parent/root binding, first retirement cause/time and immutable deadline. Account preparation captures all owned operations across orgs; root retirement captures only exact affected rows. Account deadline and source deadline combine by minimum. Capture unpublished/reserved operations too. Use the actual first committed claim event, never final storage completion. Existing historical roots whose bindings no longer exist require an explicit fail-closed repair disposition; do not fabricate a capture or silently start a fresh clock.
- Patch the actual claim/preparation producers and candidate barrier with preimage/postimage checks. Preserve owner-before-source lock order; where a request/item is already locked, use nonblocking owner/source acquisition and transaction retry. A failed transaction leaves no new clock. Source registration for previously unbound R03 calls is a separate prerequisite before declaring automatic-retirement coverage complete.
- Add a separately versioned bounded owner-wide disposition export, mandatory for the privacy worker even with flags off. Preserve current nine collections and API shapes. Give its own metadata capability and explicit denied-by-default data EXECUTE. Refresh every changed checker/profile pin from actual source bodies; do not broaden the frozen 19-key feedback profile by inference.

The subsequent expiry transaction needs a bounded due-item claim/sweep API driven by DB time, not `RETENTION_DAYS` or the resume upload cutoff in `runRetentionSweep`. Source-retired operation expiry is independent of account expiry, so unrelated active roots/owners remain usable. Capture closure locks, original-month contributions and unknown exposure, then atomically write restricted month-only aggregates, remove the exact identity closure, and advance the restore floor. All settlement/reconciliation APIs must refuse expired selectors rather than recreate rows; races linearize before the deadline or lose to expiry. A scheduled cadence cannot justify retention past the maximum: use a safety-margin wakeup/deadline monitor and record missed deadlines as failures. No scheduler exists for this lifecycle today.

Retained aggregate keys may contain only original UTC month. Separate shared-quota known tokens from R03 technical tokens/cost to avoid double debit. Fold legacy/A12/A13 using the existing validated partition in `read_initial_feedback_usage(uuid,uuid)`; R03 attempt `period` and A12/A13 `claimed_at` remain the original-period authorities. Exclude owner/org/source/op/attempt/run/actor/request IDs, exact event times, selectors, receipts and hashes from retained aggregate or purge output. Unknown holds never become zero, refunds or automatically released capacity. The accepted global hold applies when removing attribution makes exact limits unenforceable; a 31-day current-month known-usage edge blocks execution through that UTC period end. Unresolved exposure remains blocked beyond identity expiry until controlled aggregate reconciliation. Callers get fixed blocked/unavailable responses, never global totals.

Restore must quarantine snapshots, disable sessions/dispatch, replay retained dispositions before access, then enforce an owner-free monotonic minimum eligible snapshot floor after expiry. The authority for that floor must survive rollback independently of the restored snapshot. A timestamp inside the backup alone cannot provide this. Never retain an owner/hash deletion list indefinitely as a substitute. External Auth/object failure is a deadline breach/adoption blocker, not an extension.
