- `app/lib/server/supabase.ts` uses `@supabase/ssr`, propagates cookie/cache headers and sets HttpOnly, SameSite=Lax cookies, Secure for HTTPS. `getAuthenticatedUser` validates through `getUser`; retain these boundaries.

Reusing an existing Supabase user should avoid another insert; this is an expectation requiring authenticated verification, not a proven linking result.
- Local `supabase/config.toml` has `site_url = "http://127.0.0.1:3000"`, `additional_redirect_urls = ["https://127.0.0.1:3000"]`, no Google block and manual linking disabled. App config defaults to `http://localhost:5173`. Reconcile origins explicitly; no settings were changed or queried remotely.
- `safeReturnTo` rejects absolute URLs and `//`, but accepts `/\untrusted.example`. A Node URL-parser check returned `https://untrusted.example` when resolving that value against `https://app.resumide.example`. This reproduces unsafe normalization, not a live callback exploit. Existing `tests/unit/auth.test.ts` lacks this case.

## Proposed flow

1. Add a separate Google POST form on `/auth`, above the existing email form. Use the existing design tokens, accessible loading/error states and [Google button branding](https://developers.google.com/identity/branding-guidelines). A server-parsed `GOOGLE_AUTH_ENABLED` flag defaults to false; disabled requests never contact Supabase OAuth.
2. Dispatch only explicit `intent=google` to OAuth; preserve absent intent as the existing email submission. Reject unknown intents. The Google branch requires a matching Origin or same-origin Referer, including rejection when both are absent. Existing `assertSameOrigin` permits absent headers, so it is insufficient alone for this browser login initiation. Never derive callback origins from request Host or forwarded headers.
3. Use the existing server client and `signInWithOAuth({ provider: "google", options: { redirectTo: APP_ORIGIN + "/auth/callback", skipBrowserRedirect: true } })`. Respond with HTTP 303 to the returned authorization URL, retaining all Set-Cookie and cache headers, including the PKCE verifier. Validate the returned URL against the configured Supabase Auth origin and authorize path before redirecting. Missing URL or provider failure yields a generic recoverable error.
4. Use a fixed Google callback URL without `next` query parameters. Preserve a bounded, validated return path in a host-only HttpOnly, SameSite=Lax cookie, Secure on HTTPS, Path `/auth/callback`, maximum age 600 seconds. It carries navigation only, never OAuth state, tokens, user IDs or authorization. Supabase owns OAuth state and PKCE validation. Clear this cookie on success or failure; revalidate its value on consumption. Missing/malformed cookie means `/`. A second concurrent login may replace the navigation destination; it must never change identity or ownership. Retain the existing query-based `next` for email callbacks; give that explicit email path precedence and do not consume a stale Google destination.
5. Redirect chain: application POST -> Supabase `/auth/v1/authorize` -> Google consent -> Supabase `/auth/v1/callback` -> application `/auth/callback?code=...` -> safe local destination. The two callbacks have different roles. Exchange exactly once through the existing client; forward every cookie/cache header on success and failure. Handle denied consent, missing code and exchange failure using a neutral OAuth error state rather than claiming an email link expired. Do not echo provider descriptions, codes or query strings. Callback responses must not be cached.

The API and PKCE contract come from [Supabase Google sign-in](https://supabase.com/docs/guides/auth/social-login/auth-google). No One Tap script, new auth framework, custom Google token verifier, dependency or schema migration is proposed.

## Identity, sessions and tenant safety

Supabase documents automatic same-email identity linking and safeguards for unconfirmed identities. Keep that decision inside Supabase; never merge profiles, organizations or candidate data by email, Google profile fields or client-supplied IDs. Test confirmed-email linking in both login orders before enabling the feature. Different-email linking, merging and unlinking UI are deferred; keep manual linking disabled. [Supabase identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking).

Authorize every request from the validated Supabase user ID and existing organization membership. Google metadata is display data only. Preserve server-side ownership checks, consent, private storage, session refresh/logout/revocation and indistinguishable cross-owner denial. Do not persist provider tokens separately or put them in loader data, browser storage, logs, screenshots or worker payloads. Inspect actual SSR cookie serialization for provider-token fields during authorized testing; prevent unnecessary provider credentials from being retained while preserving Supabase session renewal. Login must not grant consent for resume processing or AI inference. For an already authenticated user, do not silently replace the session through the sign-in form; return to their workspace or require explicit sign-out before choosing another account.

Cross-provider coordination: Google follows the documented Supabase behavior above. ChatGPT identity has separate ownership-confirmation requirements under its companion design. Do not activate a custom ChatGPT provider until that linking contract is proven; do not introduce a parallel application identity store to bypass it.
