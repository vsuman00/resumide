## Existing source and Supabase compatibility

Source inspection found email `signInWithOtp` in `app/routes/auth.tsx`, Supabase `exchangeCodeForSession` in `app/routes/auth.callback.ts`, and `auth.getUser()` in `app/lib/server/auth.ts`. `app/lib/server/supabase.ts` writes HttpOnly, SameSite=Lax cookies, secure for HTTPS. The membership bootstrap in `supabase/migrations/20260909110000_membership_authorization.sql` binds UUID `auth.users.id` to a personal organization. Preserve that user, workspace and all ownership checks.

The preferred candidate is Supabase Auth's [custom OAuth/OIDC provider](https://supabase.com/docs/guides/auth/custom-oauth-providers), for example `custom:openai`. It documents discovery, JWKS validation and server-managed PKCE/nonce. This is not verified compatible with Resumide's deployed Supabase or installed SDK. Its documented client-secret setup must match the actual OpenAI provisioned method (`none` or `client_secret_basic`), discovery, claims and email behavior. Keep PKCE on and nonce checking enabled. Verify these contracts before selecting it.

This broker flow has two callbacks: OpenAI returns to the exact Supabase provider callback registered with OpenAI; Supabase then returns its own code to Resumide `/auth/callback`. Never pass an OpenAI authorization code into `exchangeCodeForSession`. Fixed environment origins and explicit redirect allowlists must cover production and approved test domains; arbitrary Vercel preview URLs are excluded.

[Third-party Custom OIDC](https://supabase.com/docs/guides/auth/third-party/custom-oidc) is a different JWT trust mechanism. It requires role claims and can require text-subject/RLS changes; it is not evidence that an OpenAI ID token becomes the current Supabase cookie session. Do not replace `getUser`, UUID ownership or RLS with direct OpenAI JWT trust. If the broker cannot meet the contract, stop for an ADR and a supported session bridge; do not mint ad hoc Supabase sessions or add a parallel session system.

## Identity mapping and account linking

Treat `(issuer, provisioned client ID, verified sub)` as the external identity key, scoped to environment. Supabase remains the local user/session authority. Record only required mapping/profile fields; neither email, display name, callback parameters nor an opaque host ID authorizes workspace access. Any additional mapping table needs a coordinator-owned forward-only migration and uniqueness/concurrency review.

A linked subject resolves to its existing local user. A new subject creates a new account only under the accepted onboarding contract. Linking to an existing account requires a fresh authenticated local session, explicit user action and confirmation of both identities; bind the pending link to that user and consume it once. Reject subject collisions, account switching during callback, concurrent claims and stale sessions. Never merge memberships, resumes or organizations on an email match. Unlinking must retain a tested recovery method and must not transfer data.

There is a material prerequisite: Supabase documents [automatic same-email linking](https://supabase.com/docs/guides/auth/auth-identity-linking), whereas the [OpenAI website policy](https://developers.openai.com/siwc/website) requires ownership confirmation. A confirmation screen after an automatic link is too late. Prove a supported configuration/control that prevents unconfirmed linking before issuance, or keep this provider disabled. Do not assume manual linking alone disables automatic linking. The coordinator must reconcile this policy with Google and magic-link accounts.

## Authorization transaction and session acceptance

For a direct OpenAI flow, the future backend must generate cryptographically random state, S256 PKCE verifier/challenge and nonce per attempt. Store a short-lived, one-use transaction in a shared durable store bound to a secure browser cookie, intended operation, local user for linking and validated return path. A process-local map is unsuitable across Vercel instances. For the preferred broker flow, Supabase owns the upstream transaction; prove equivalent protection rather than duplicating or overriding reserved parameters.

Validate state, expiry, browser binding and authorization errors before any exchange; consume pending state atomically even on failure. Use the exact registered redirect and provisioned client authentication. Validate the ID-token signature with an approved JWT library and trusted discovery/JWKS, including issuer, client audience, expiry, issued-at and nonce. Pin trusted issuers/endpoints, constrain clock skew and key refresh, and reject algorithm/key confusion. Never trust token-provided URLs. Clear temporary state and rotate the application session after success. Keep callback responses uncacheable and strip code/error parameters from redirects. The [website guide](https://developers.openai.com/siwc/website) supplies the upstream contract; these serverless storage and redirect constraints are proposed engineering requirements.

Retain the current Supabase cookie attributes, server-side validation and safe same-origin return behavior. Test backslash, encoded and protocol-relative return paths. Identity sign-out clears the Resumide session; it does not claim to sign out of ChatGPT. Identity mapping alone stores no inference credentials, and raw identity-only ID tokens should be discarded after validation unless separately justified.

## Optional plan connection and credential lifecycle

Keep login identity and AI connection separate. A candidate already signed in by email/Google may request a ChatGPT plan connection without changing the local account. Give the connection explicit states: unavailable, disconnected, authorizing, connected, expired, revoked and limited. A valid identity without the granted plan permission retains login but disables plan usage. Do not infer funding from login method or a claimed subscription.

The published OSS request includes `offline_access resource.invoke chatgpt.tokens.use.direct` in addition to identity scopes and a resource of `https://api.openai.com/v1`. These are reference requirements, not a hosted grant specification; confirm the approved hosted contract before using them. [Sign-in reference](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).

Subject to that approval, store tokens encrypted in server-owned storage, with owner user ID, verified external identity/client, granted scopes, expiry, credential version and revocation state. Store encryption keys separately. No tokens in cookies, browser storage, logs, telemetry, job payloads or handoffs. Jobs carry an opaque connection reference and recheck owner, consent, grant version, funding selection and revocation at execution. Serialize refresh and atomically rotate credential sets; reject identity changes on reauthorization. Local disconnect disables future work and deletes usable credentials, with best-effort cancellation of in-flight requests; an already sent request cannot be recalled. Account deletion includes connection deletion. Do not promise an undocumented remote revocation endpoint.

OpenAI currently sends no disconnect notification. Confirmed revocation/terminal refresh errors require reauthorization; temporary network/503 failures preserve credentials and use bounded retry. A limit stops plan-funded work and links to ChatGPT usage settings. Never switch silently to app-paid inference. [Lifecycle](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions), [recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).

After separate hosted approval, discover account-specific models and validate capabilities. The current reference flow uses public Responses HTTP with `store: false`, `stream: true` and completion only at `response.completed`; no ChatGPT backend endpoints. Preview restrictions prohibit several conventional request fields, including `max_output_tokens`, so existing adapters need a contract audit and a supported output/resource bound before use. Do not assume provider parity. Data minimization and explicit candidate AI consent remain necessary. [Models/inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference), [limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).
