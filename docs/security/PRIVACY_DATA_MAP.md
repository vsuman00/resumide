## Boundaries and ownership

The browser uses authenticated React Router server routes. Supabase directly provides PostgreSQL, Auth and private resume Storage; Docker is worker/compiler-only. Server secret credentials permit privileged access, so routes and authority functions must independently check ownership, membership, active source, deletion and concurrency. Declared grants/RLS do not prove current project access; grants and row policies are separate controls. [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

Immutable evidence, old versions, UUIDs, object keys, hashes and request IDs can remain personal or linkable data. They are not anonymous merely because they are metadata. Candidate confirmation, deterministic scoring and AI proposals have separate authority. Services currently remain free of commercial charges; technical quotas are not payment/subscription records.

## Auth, source access and caching

Current sign-in uses email OTP, callback code exchange, and server-side `getUser`. Logout calls Auth sign-out and reports an unconfirmed result if Auth returns an error. Any session cookie removal requested by the SDK still applies. SSR cookies are HttpOnly/SameSite Lax, secure on HTTPS, with a configured max age of 3,600 seconds by default. Live email delivery, Google and ChatGPT OAuth, token lifetime, all-session revocation, and provider retention have separate evidence requirements. [Managed Auth checks](../operations/MANAGED_TESTING.md#run-the-protected-authenticated-browser-job)

Storage uploads without upsert and permits signed URLs for at most 300 seconds (default 60). These are temporary bearer capabilities, not public objects or permanent revocation guarantees; never log them. Private canonical/privacy/Build responses declare no-store policies. Actual tenant, shared-cache, direct-resource and stale-session checks remain open.

The private source PDF route checks the exact organization, resume and version key before downloading. It rechecks the caller's access and source binding after Storage responds. The response carries the PDF only if its length and SHA-256 match the saved version. Local Chromium verified owner access, byte mismatch refusal and equal private 404 responses for anonymous, foreign and revoked access. Managed Storage and history-session acceptance remain open. Progress uses the signed-in query and checks the source and account again after reading OCR recovery. The progress page removes a previously shown status when polling returns an access denial. ## AI and local-worker transfer

Analysis/rewrite can send saved resume text, job title/description and source references to the configured OpenAI API after versioned consent and applicable admission. Their transports differ; do not infer one retry/log/storage policy across every AI surface. The endpoint rule permits the official HTTPS API path on its default port. It is not a provider retention, training or zero-retention agreement.

Build AI receives the full buffer at the application server for validation, then constructs the provider request from selected text and bounded before/after context. It does not attach the full buffer/hash or application owner IDs to that payload. Selected text may itself contain personal data. The transport requests `store: false`, disables SDK logging/retries and rejects redirects; these settings do not prove provider-side deletion. Build consent/audit/counters persist separately, while source/proposal content is not saved by this service.

Local OCR/compiler adapters transfer document bytes/source through worker input and bounded output/scratch. OCR diagnostics can contain document text and are counted/discarded; compiler responses use fixed categories. Automatic upload OCR integration/quality and the current compiler's positive runtime/confinement path remain open. Public dependency archives and synthetic build receipts are separate from candidate content.

The synthetic local OCR review preflight checks an active fixture, grant, worker identity and matching retention policy before rendering. It creates neither a durable grant nor a deletion schedule. ## Retention and deletion graph

`RETENTION_DAYS` defaults to 30 in source; this review did not read the active environment. The sweep selects resume roots by `created_at`, not an independent expiry for every row. Claiming marks a root deleted, records exact keys in private retention items, then removes each object before completing its item. Completion deletes the root only when all recorded items are deleted; failed storage cleanup remains retryable. Scheduling/liveness/success are separate operational evidence. No all-store 30-day deletion guarantee follows.

Owner deletion follows this declared sequence:

1. The server inserts an owned durable request and audit event. A successfully cancelled still-queued deletion is withdrawn: failed/cancelled requests are inactive, while queued/processing/completed and unknown states block the current access guard. The shared predicate is used by canonical/JD access, privacy download and the privacy page. A forward owner/write barrier is being prepared; actual enqueue/write serialization remains unproved until its SQL is reviewed and executed.
2. A leased worker claims the request. `prepare_deletion_request` locks the request, durably records its exact object plan and transactionally deletes owned analyses, jobs, resumes, consents, memberships and profile. Its present cleanup order is analyses before resumes; coordination with root/analysis writer locks needs proof/alignment.
3. Declared foreign keys cascade analysis/resume/source/version deletion to dependent evidence/corrections/results/AI runs/canonical/requirements/authoring data. This is a schema contract, not a fresh exhaustive cascade test.
4. The worker removes saved objects by exact key and performs a fresh Storage metadata lookup for each key. Only an explicit object-missing response qualifies. A still-visible object, ambiguous response, or timeout uses the existing failure and retry path. Successful completion marks the request completed and removes its private plan. The lookup measures visibility through the Storage API. Bound admission records still require separate writer reconciliation and retirement.

For interrupted tracked uploads, the private cleanup progress row follows the existing request inventory. It stores the latest claim that verified new cleanup and the count of verified handoffs. The owner export includes both counters with that inventory. Account retirement must cover the inventory and its progress together.

The private cleanup receipt links the captured request and upload to the attempt that issued verification. It records the first verified absence timestamp and appears with the same owner inventory. The receipt uses the existing upload transport record for the acknowledged object ID and the existing upload ledger for the exact key. Retirement must cover all three linked records.

The adopted source binding links the current deletion inventory and adopted upload to a digest of the exact source and acknowledged Storage identity. It includes the original match time and claim attempt in the owner inventory. A binding records database evidence about the source and queue. Managed object absence and final ledger retirement require separate verification.

The adopted deletion handoff stores the captured upload IDs, a hash of the durable object plan, and its first preparation attempt and time. The owner export includes those fields in the captured deletion inventory. The handoff keeps the exact Storage identity available through the existing upload transport and records verified absence in the same request-scoped receipt.

After every captured upload has a verified absence receipt, the retirement transaction removes the exact admission operations, uploads, transport records, captures and linked metadata. It also completes the sealed request and preserves the owner write barrier. Local PostgreSQL verified rollback and preserved unrelated rows. Actual managed Storage cleanup is still pending. [Verification](../../tasks/agent-handoffs/2026-11-09-reliability-implementation/admission-ledger-retirement-closeout.md)

The inspected function does not delete `auth.users`, Auth sessions, owned organizations, audit rows, other `data_requests` or their earlier export manifests. Full-account erasure and removal of all duplicated personal content are therefore unproved. No deletion deadline for hosted backups/replicas, provider logs or user/operator local copies is established by this review.

## Privacy export versus document export

The privacy worker saves a `resumide-export-v1` JSON manifest of owned profile/membership/consent/request metadata, analyses/jobs/resumes/file metadata, results/drafts/extractions, evidence/corrections, workspace records and audit rows. The workspace RPC combines canonical versions/facts/heads/change events, requirement versions/items and authoring events in one stable SQL snapshot. Other worker queries are separate; the whole manifest is not one cross-table MVCC snapshot. Files are listed by key/checksum/size, not embedded PDF bytes.

Download requires that owner's completed request and returns attachment/no-store headers. The route checks for that owner's blocking deletion before loading the manifest and again before serialization, excluding failed/cancelled requests; an unverifiable policy query fails closed. The privacy page separately queries the full owner-scoped blocking predicate before limiting it to one row, so its twenty-row history page cannot authorize downloads. It exposes only allowed/blocked/unavailable access metadata; the download API remains authority. Source review and mocked route/component tests support these guards, not atomic deletion-enqueue/response ordering or hosted enforcement. `data_requests.result_manifest` is another durable personal-data copy. Job export currently selects metadata without the raw description; the worker does not directly select `analysis_ai_runs` or private admission/retention collections. Coverage, row completeness and omission policy need review. The local ledger/privacy source now extends the stable workspace RPC and worker schema together with five correction and five association metadata collections. These arrays are required, preserve owned row fields and reject missing, malformed or foreign metadata. The worker therefore requires the paired SQL update; older incomplete responses fail closed. The new stores have scoped cascade references, RLS, immutable-update and privacy-write guards. These SQL contracts remain unparsed and unexecuted; actual cascade, erasure, retention and native export completeness remain unproved. See the [current local result](../../tasks/agent-handoffs/2026-11-09-reliability-implementation/a02-atomic-import-closeout.md).

Privacy create/cancel service contention is mapped to a fixed retryable 503 action result, preserving private/no-store and session headers. The page shows an action error rather than treating a temporary barrier conflict as success. This source behavior does not prove actual hosted lock contention or request processing.

Canonical PDF/DOCX export instead requires confirmed current content and rechecks the exact head after rendering. An original quote must not support replacement text. Generated/downloaded document bytes are distinct from the durable privacy JSON export.

## Grouped-import retry metadata, 2026-11-13

The canonical review page keeps one pending grouped-import command per owner and analysis in tab-scoped `sessionStorage`. It stores source/model identifiers, hashes, captured revision pairs, selected group IDs, output locale, the original request key and a save timestamp. It stores no extracted values, resume/JD text, tokens or checked state. These identifiers remain linkable personal metadata.

The command is limited to 16,384 bytes and must also fit the encoded submission limit. A record expires after 30 minutes; malformed, foreign, future-dated, expired or source-mismatched records are removed from that exact namespace. A matching successful receipt clears the record. Other account namespaces and ordinary drafts are untouched. Storage failure keeps a retry in page memory and tells the candidate that reloading may lose it. Browser-controlled storage is not a server retention or deletion guarantee.

The stored command retains its prospective relationship-acknowledgement field. Actual checkbox acceptance is transient: restore, retry and persisted history restoration require a fresh visible named acknowledgement. Nothing submits automatically. Changed current heads or captures do not rewrite the retained command; the server checks its owned source again and the transaction decides exact replay before a fresh write.

The new read RPC exposes the raw envelope only to the server. The page receives bounded derived groups and owned citation links. Read permission and writer permission are separate; the writer remains revoked. These are local source and synthetic test boundaries, not proof of applied grants, native transactions or managed browser privacy.
