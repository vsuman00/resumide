# A13 feedback producer and publication design

Design only, 2026-11-15. Root assigned this document alone; no production source, tests, shared contract, policy, schema or migration was changed. A12's twelve released files remain frozen. This proposes the next implementation; it is not a new frozen protocol or acceptance result.

## Actual boundary and reproduced gap

The governing task is CR-A13, blueprint alias A12 in [the ATS plan](../2026-11-09-reliability-plan-ats.md#a12-apply-the-same-support-contract-to-qualitative-feedback). The required outcome covers factual tips and explanations as well as summaries and bullets; questions must remain distinct. Deterministic numbers and safe unavailable states stay unchanged.

[qualitative-prose.ts](../../../app/lib/server/qualitative-prose.ts:34) validates writer output through the existing support IR but admits each tip solely through substring quotation identity. Its title and explanation receive no factual support check. [qualitative-ai.ts](../../../app/lib/server/qualitative-ai.ts:235) uses that helper before legacy projection. [result-feedback.ts](../../../app/lib/result-feedback.ts:4) and [CitedWritingSuggestions.tsx](../../../app/components/CitedWritingSuggestions.tsx:36) infer cited-note visibility from quote presence; neither consumes persisted support proof.

Frontend's frozen real-helper/AI-wrapper/presenter test has 11 failures and six passing controls across 17 cases. Exact-source citations still allow fabricated revenue, agency, skills, causal outcomes, polarity, direction, qualifications and cross-contribution metrics in titles/explanations. The deliberately bad provider response also survives the actual AI wrapper and enters presenter counts. Useful editorial advice, exact source claims and explicit evidence questions already have passing controls; those must stay useful. The preserved downstream writer failure is already withheld and must not be reopened. ## Proposed pure interface

Add a strict, separately versioned qualitative-support sidecar; preserve frozen Feedback and legacy compatibility scores. Proposed APIs are `deriveFeedbackSourceManifest(ownedContext)`, `validateFeedbackPlan(ownedContext, rawPlan)` and `projectFeedbackPublication(validatedResult)`. They accept the actual validated owned context, never caller support flags or prebuilt witness arrays.

A context binds owner/organization/analysis, resume/source version and file hash, the selected text/native-content hash, exact JD snapshot/hash, extraction or evidence producer, current canonical/JD versions and heads when present, deterministic result checksum/rule versions, consent/retention and support/prompt/model policy. Lease and dispatch attempt are technical identities, not candidate evidence. Source refs retain exact Unicode-code-point ranges and their named offset space, source/fact IDs, current value, confirmation basis and whole source context. A citation proves quotation identity; it does not prove the new sentence.

Each result item has category, kind (`source_claim`, `editorial_observation` or `clarification_question`), support state (`supported`, `clarification_required` or `rejected`), source refs, exact title/explanation support operations and fixed reason codes. Do not persist or render rejected raw prose as supported. Questions are separately presented and cannot count as strengths or accepted resume facts. Unsupported assertions cannot become safe questions by adding a question mark; use non-presupposing reviewed question templates with bound source/JD parameters.

The provider selects a bounded source/finding/question/transform plan. The server reconstructs concrete text where possible; any remaining factual title and explanation must each pass the same source relationship checks. JD may select relevance or supply a visibly labelled question, never a candidate skill or qualification. Source support preserves actor, negation, metric governor/unit/direction, time and ownership. Current confirmed declarations retain declaration labels; historical quotations cannot certify edited text. Numerical observations come only from admitted deterministic finding IDs, never model calculations.

Use the existing [writing support IR](../../../app/lib/server/writing-support.ts:103), including layout normalization, independent-clause ordering and explicit supported role/contribution composition, alongside equivalent actions and exact copies. Require useful positive examples for factual observations, clarity edits, supported summaries and truthful missing-evidence questions. Neither all-empty output nor only action synonyms satisfies full A13. Unknown relationships abstain or request clarification. Retain actual caps: four items per existing category, four writer bullets, current projection lengths and the existing IR resource ceilings; never truncate source to make evidence appear unqualified. Expanding that support envelope requires a reviewed producer and native counterpart.

## Necessary owned-source dependency

The current worker has no canonical/JD snapshot. [qualitative-stage.ts](../../../app/lib/server/qualitative-stage.ts:75) reads extracted text, mutable job text and a deterministic score/trace. It omits the extraction checksum and deterministic input/result checksums already stored in their tables. Both scoring and qualitative stages intentionally stop for v2 evidence through `hasUncalibratedEvidence`. Keep that guard and existing no-score semantics effective.

Freeze a discriminated read context rather than invent canonical IDs:

- `legacy_extraction`: actual owned analysis/source tuple, extraction row keyed by analysis ID, text checksum/native content hash, extractor/page metadata, deterministic input/result checksums and exact owned job snapshot/hash. This supports observations about the source text, not confirmed canonical attribution. Since jobs are mutable, archive the exact selected source/JD snapshot in the immutable publication and compare it at finish; a bare job ID is insufficient.
- `canonical`: the actual owned relationship context, selected canonical/JD native hashes, current fact/value/confirmation/source lineage and captured heads. Reuse its real proof budget. Prefer this source when it exists; never silently fall back to stale extraction after an owned read fails. The initial v2 worker currently cannot reach this tier because the deliberate uncalibrated guard stops earlier. A separate admitted post-review feedback invocation is a necessary follow-up dependency, not permission to remove the guard, fabricate confirmation or silently add a new entrypoint now.

A12's confirmed-only rewrite manifest is draft-coupled and cannot replace this initial-source reader. Generic cited editorial feedback need not pretend every initial source statement is owner-confirmed; label observed text accurately. Applying any generated candidate change still requires the existing explicit review/confirmation path.

## Native publication and lifecycle proposal

Suggested service-only seams, subject to Root's contract freeze: `prepare_initial_feedback(analysisId, lease, policy)`, `claim_initial_feedback(analysisId, lease, operationId, bindingSha, budgetOrNull)`, technical `settle_initial_feedback_attempt(...)`, and `finish_initial_feedback(analysisId, lease, operationId, bindingSha, plan, usage)`. Prepare returns an owned operation/status and a nonnull context only for new preparation. Claim alone authorizes a single attempt. Both budget modes require durable claim identity; budget-on atomically invokes the existing ledger claim. Known retryable failures may use the already bounded, separately identified next worker attempt; an ambiguous same-attempt retry must never redispatch.

The existing lease [wrapper](../../../app/lib/server/analysis-stage-fence.ts:121) and [native lock](../../../supabase/migrations/20261110082455_analysis_stage_write_fencing.sql:25) protect worker lease, owner, membership, active source and deletion. They do not validate new prose or compare captured JD/canonical/checksum bindings. [persist_qualitative_analysis](../../../supabase/migrations/20260909220000_qualitative_ai_stage.sql:52) atomically inserts run/result/writer and transitions state, but trusts caller JSON. Its versioned successor must independently reconstruct/check the admitted source/finding/question/IR plan, copy deterministic values from the stored row, and recheck the exact lease/privacy/consent/source/JD/canonical binding under locks before publishing.

A minimal storage candidate is one metadata-only operation/attempt family plus one immutable feedback publication containing its exact source snapshot, per-item support and projection. The existing result row can carry a nullable publication reference; old rows stay visibly legacy-unbound. This avoids assuming arbitrary old run output is proof. Any new store requires paired privacy export/deletion coverage before adoption. Do not freeze table names or add grants from this proposal. Guard the actual worker readiness preimages and explicitly enumerate changed/new routines; no activation or broad legacy public grant.

Exact owned saved/status replay precedes fresh-head/rate/provider work; privacy/ownership admission still occurs first. Provider keys bind owner/analysis/operation/source/model/prompt. Settle known usage before validation/publication and preserve it if later accounting fails; unknown usage remains unknown with its hold. Cancellation, lease loss, unsupported output and stale source cannot publish a current supported run or replace the prior draft. Ambiguous finish retains its exact operation for receipt recovery. Partial results retain deterministic checks and explicit unavailable prose. A provider success or a nonempty safe projection alone does not justify completed supported status.

## Bounded implementation sequence and acceptance

1. Shared producer leaf: new qualitative-support module, existing qualitative-prose and qualitative-ai, focused support regression test, handoff (five files). Reuse the frozen 17 real boundary cases; preserve safe editorial/question/source positives and add only source/version controls needed by the new interface. This closes the direct factual-tip escape but is not full A13 acceptance.
2. Native/owned-reader leaf: forward migration, strict context adapter, source-contract test, deferred rollback-only verifier and handoff (five). A paired privacy worker/test/handoff leaf follows before adoption. Native support checks must be real counterparts, not trusted JS booleans or digest claims; any unsupported transform capability stays explicit.
3. Worker integration leaf: qualitative-stage, analysis-stage-fence, stage/outage tests, fence tests and handoff (five). Bind read/claim/settle/finish, fresh and prior ordering, cancellation/lease loss, deterministic partial behavior and both budget modes. Preserve old numerical and uncalibrated tests.
4. Consumer leaf: typed support presenter, result-feedback compatibility projection, actual owned route loader, actual consumer test and handoff (five). Persisted and displayed support states must match; questions and historical/unbound publications are visibly distinct, with no rating or strength inferred from quote/nonempty text.

Root coordinates exact schemas, version dispatch, ownership, default-off admission and combined checks before dependent writes. Full acceptance requires positive useful feedback through the actual worker, native publication source and actual presenter, plus stale/foreign/policy/replay/cancel/known-usage refusals with prior data preserved. Synthetic/source checks, native transactions, live delivery, representative usefulness and release approval remain distinct. No A12 audit or closed campaign is requested again.
