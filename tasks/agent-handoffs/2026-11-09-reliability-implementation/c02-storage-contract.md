Prepared 2026-11-09, Asia/Kolkata. **Review proposal only; no SQL, schema, producer, RPC or application change is authorized by this packet.** Root integrated A03 at `439c6f16…` / `d7da2e2b…`; its projection is read-only and does not prove application, complete history or write authority. ## Recommendation

Use one service-only PostgreSQL transaction wrapper around the existing `save_canonical_version` import/edit validators, plus an immutable correction ledger outside canonical JSON. First implement mapped existing facts. A corrected initial import can create the original sourced import and then clear-citation, unconfirmed edit children **inside that one transaction**. Return the final head as one candidate action and expose its internal version sequence in history. Independent JavaScript RPC calls are not atomic and are excluded.

This preserves `canonical-resume/1.0.0`, both admitted historical producers and the stronger existing SQL checks. It avoids inventing a batch event inside canonical JSON or weakening ordinary import. It does **not** implement `requires_add`: a separate reviewed candidate-authored add operation is mandatory before the full correction path closes. Side-ledger storage is recommended here, not yet selected/admitted for writing.

## Minimum ledger and read binding

Recommend three small normalized collections rather than embedding provenance or repeatedly scanning JSON command arrays. Exact names/constraints remain migration review work:

1. **Correction operations:** immutable outer idempotency receipt, owner/org/resume/analysis/source/attempt, target/projection/admission versions, expected review and assignment heads, expected canonical head, normalized selections, exact final version/revision, created child/application IDs and request metadata. One unique idempotency key per owned resume operation. Values come from stored events; a client-supplied proposed value/body is not authority.
2. **Target assignments:** immutable event-to-assertion/slot bindings with model/source/attempt tuple, owner actor, assignment revision and explicit selected canonical location when applicable. This supports indexed per-target replay and preserves choices for legacy null-candidate events. Binding changes require an explicit new reviewed assignment/reassignment, never an update or silent retarget. Bind concurrent decisions to an **assignment head**, because correction revision alone does not change when a mapping decision changes.
3. **Fact applications:** immutable operation/assignment/event references, base/result canonical version, fact/location IDs, actor/revision and original citation references. The replacement value lives in the canonical fact; its original refs live here as review lineage, never as replacement support. Do not duplicate source text unnecessarily. Composite ownership/source/version relationships and append-only enforcement must prevent cross-tenant joins.

The read DTO joins these alongside historical canonical JSON. Historical versions with no ledger remain valid with explicit `legacy_no_application_record`, not fabricated attribution. A03's `unchanged_provenance` is not evidence of an applied row. Add actual application/undo disposition only after an owned ledger read. Recommend public tables consistent with the existing canonical collections: owner-only active-source/membership/deletion RLS, explicit read grants, immutable triggers, revoked client/direct service writes and service-only authority functions. Service credentials bypass RLS, so the functions still need their own ownership checks. [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

Opaque target IDs are selectors, not authority. SQL must reload the immutable assertion and verify field, exact ranges, source/attempt and supported target-model version. Do not assume PostgreSQL jsonb serialization reproduces the TypeScript hash's object-key order. Either share an explicitly reviewed cross-language serializer or persist/verify the underlying target tuple and use the opaque ID only as a consistency label. Candidate group IDs remain unverified context.

## Atomic apply protocol

1. The server authenticates the actor and reloads current owned analysis/source, complete review/assignment snapshot and canonical head. The command names exact event/target/location choices, expected heads/versions and an idempotency key. A03 output or a browser snapshot cannot authorize it.
2. Use the coordinator's stable **resume/root → analysis → review/assignment/head** lock order. Existing canonical/authoring writers already serialize on the root; correction/evidence writers serialize on the analysis, which supplies the shared review-revision barrier. Check active ownership, organization membership, source/checksum, consent/deletion scope and supported models. The current privacy deletion function deletes analyses before resumes; its lock ordering must be aligned or otherwise proved safe before activation, rather than relying on a racy pending-deletion check. Include forced apply-versus-deletion tests in that reviewed leaf.

   The barrier must include **deletion request creation**, not only cleanup. `privacy.ts:55` currently inserts the request directly: enqueue could commit after apply's pending-deletion check without taking either lock. The concrete forward packet must select a shared enqueue/apply serialization barrier (including multi-resume scope) or prove an equivalent ordering guarantee. Do not infer that the root/analysis locks alone solve this race. Force enqueue-versus-apply and cleanup-versus-apply interleavings before activation; no lock/DDL mechanism is silently selected by this clarification.

3. After access checks, an identical prior outer key returns its **original final result** without rerunning children or moving the current head backwards. A conflicting normalized payload returns conflict. A fresh operation checks latest active attempt, authoritative review revision, assignment head and expected canonical head under the same locks. No stale read-prefix attestation is sufficient.
4. Resolve assignments before per-target latest selection. Confirmations bind exact assertions but never canonical-confirm. Legacy multi-target events require explicit choices; unresolved newer events cannot be discarded to make an older correction apply. Canonical identity needs exact type/citations or bounded gapless owned origin proof. Manual edits receive a current/proposed diff and explicit selection; never match solely by value or overwrite all employers.
5. For initial import, create the ordinary sourced draft through the old validator, then perform each selected correction through its existing exact edit validator. For reconciliation, start from the actual current head. All inner calls execute within the **same SQL function invocation/transaction**, with explicit inner CAS and distinct step keys. Any non-applied inner result must raise/abort the whole operation; returning a partial conflict after an earlier insert would commit a broken action.
6. Each corrected edit is unconfirmed with empty sources/null confirmation. Insert assignments/application lineage and the outer receipt in that same transaction, then expose only the final head as the result. Intermediate immutable versions remain honest history. Canonical confirmation is a separate exact version/fact/value action; export stays blocked until it succeeds.

A repeated apply must also consult application history: an event previously applied and then manually edited/undone is not automatically reapplied under a fresh key. Require an explicit reviewed reapply/reconciliation action referencing that earlier application and the current head. This prevents unchanged raw correction history from undoing a candidate's manual work.

## Add, restore and privacy compatibility

**Add is a distinct leaf.** There is no existing add command. Design a narrow candidate-authored add validator that permits only the selected correction event's value/type, empty sources, unconfirmed/null confirmation, one reviewed owned contact/section/entry location and an explicit new stable fact ID. Preserve unrelated content and exact preview references. Do not forge a source citation, reuse an unrelated fact, or relax normal import. Review its change-event operation and producer/SQL allowlist consequences explicitly; if a producer bump is required, retain all historical readers. Until implemented and tested, `requires_add` stays visible and the parent gate remains open.

Undo/restore appends a child and records which prior application snapshot it restores. Restoring a corrected unconfirmed fact keeps it unconfirmed; restoring an older exact confirmation retains the existing rollback semantics and its historical actor/value record. An undone application remains history and must not silently reappear. Normal edit/confirm/rename/authoring children need an owned provenance join/inheritance rule; cleared or changed fact values must not inherit mismatched application support. Artifact exports remain bound to the requested immutable version, never whatever head is newest when rendering finishes.

Ledger FKs/cascades must cover owner, org, analysis/source, correction, canonical version/fact and operation relationships without orphan receipts or target choices. Pending deletion revokes reads/writes before cleanup; deletion/retention must erase these new personal records and preserve the durable storage-object cleanup plan. Extend the stable workspace export and privacy worker schema/manifest together. Historical exports remain readable with absent ledger collections interpreted as legacy, not dropped records. Restore tests must check old/new JSON, ledger links, confirmation, ownership, idempotency and deletion behavior; the existing Docker database restore script is ineligible. Actual managed restore needs RT24's new verifier and an exact isolated target allocation.

## Completeness hypothesis and bounded implementation leaves

Current ascending correction reads have no explicit completeness attestation. A capped contiguous prefix is a **source hypothesis**, not a measured project-row-cap diagnosis. First reproduce with a small capped-query fake; do not assume 1,000 is this project's cap. Then capture an owned authoritative high-water review/assignment head, page a stable ordered immutable prefix through that head and prove count/contiguity/completeness, or return explicit continuation/unavailable. Recheck heads inside apply. Exact count/range are documented capabilities; ranges are ordered and inclusive. [Select/count](https://supabase.com/docs/reference/javascript/select), [range](https://supabase.com/docs/reference/javascript/range).

A03's 1,000 events, 64 ancestors, 20,000 facts/references and 2,000,000 text work limits are not product-history support limits. Indexed latest-per-target snapshots must retain unresolved-event summaries, assignment-head binding and a completeness proof before they replace full history. Over-limit work requires continuation, not silent truncation or an authority claim.
