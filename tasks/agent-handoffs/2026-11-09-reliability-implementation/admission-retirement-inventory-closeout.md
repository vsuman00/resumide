# Scoped upload inventory for account deletion

This stage 1 and 7 change advances CR-R19 and CR-R17. When the deletion guard holds a request, the worker asks PostgreSQL to capture the complete operation and upload IDs for that account. The database validates the exact worker claim and attempt, acquires the existing owner lock, and observes all owned organizations in one snapshot. It stores the original ID set once and rejects scope drift on a later attempt. The worker receives bounded counts only. [Migration](../../../supabase/migrations/20261121132235_analysis_admission_retirement_capture.sql).

The classification distinguishes legacy, tracked but undispatched, dispatched without acknowledgement, and acknowledged uploads. It also counts recorded worker leases, invalid paths, operations without uploads, and missing or inconsistent source relationships. Even an expired worker lease remains visible. Upload rows retain the exact key and available Storage identity. The new inventory uses those existing records and does not duplicate the stored hashes or object paths. The database withholds an inventory if the number of rows exceeds the current bound. New account exports include the retained capture in the same owner snapshot and reject oversized exports explicitly.

A missing or malformed capture keeps deletion on hold and records a separate internal reason. The privacy page projects either reason to the same upload-cleanup message. No object removal or deletion completion follows from capture. A rejected or expired claim cannot create a new inventory. The recorded IDs are an input to later reconciliation. Before physical deletion or erasure, the next implementation must reacquire the live claim and owner fence, account for writers after failed requests, verify that the exact object is gone, and prove the complete scope again.
